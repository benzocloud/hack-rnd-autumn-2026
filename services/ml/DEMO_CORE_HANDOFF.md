24.10.2026. Сверка main `02ec65c1c136594755c11def50100921551bd8bc` после fetch.
Передача Core/API с воспроизводимым сценарием единого RPC.
ML-часть проверена; статус подключения полного сценария — «На ревью / не пройден».
Чужой checkout/financial.py, Core/API, Auth и канонические proto не менялись.

## Решение по ML перед демо

- Сохранять mean_90 как математическую основу; L/C/CL/CLS не прошли критерии v3.
- Для **продуктового** прогноза уже принят финансовый профиль:
  `mean_90 / mean_90_components_v1 / calendar_replacement_v1`.
  Ограниченный `mean_90_v1/daily_snapshot_v1` — только явный контроль, не замена
  финансового профиля при пустом календаре или ошибке. Автоматического fallback нет.
- Единственный RPC — `ml.v1.ForecastService/Predict`. Переключения на удалённый
  PredictFinancial, отдельный финансовый service или старые financial_pb2 нет.
- Рекомендация владельцу: C как UI-гипотезы до демо не добавлять. Подтверждённые
  ручные платежи обязательны и показываются отдельно от гипотез регулярности.
  Это рекомендация по скоупу, а не запись об уже полученном апруве владельца.
- Вероятность не откалибрована и недоступна с причиной; confidence правил и
  bootstrap-доли не становятся вероятностью. Не выдавать лимитированный сценарий за P0 целиком.

Основание: ADR-029, docs/core/financial-ml.md, proto/ml/v1/forecast.proto,
proto/core/v1/forecasting.proto и payments.proto. Более старые research-заметки
про отдельный PredictFinancial не определяют текущий wire-контракт.

## Владельцу Core

1. Внутренний worker готовит immutable snapshot с 90 покрытыми днями, accepted
   observed cutoff EOD, фактами и согласованным календарём одной data_version.
   Истинность coverage и связей подтверждает Core; ML проверяет форму/арифметику.
2. Дополнить нынешний baseline-only application DTO/Go adapter: typed calendar,
   операции/происхождение категорий, model/config/seed context; принять и проверить
   components/bands/evidence/limitations финансового ответа. Сам protobuf уже готов.
3. Вызывать Predict вне SQL-транзакции; проверять scope/model/calendar echo,
   30 дат, формулу баланса, ссылки и каждый remaining один раз. Сохранять вход,
   результат и job state; повторное чтение не пересчитывает старый прогноз.
4. Реализовать UpdatePayment/CancelPayment handlers/use cases/storage: методы
   уже определены в canonical PaymentsService. Создание/match/replay/версии должны
   сохранять действующие Auth и financial transaction boundaries.
5. Частичная оплата: фактический debit уже включён в accepted EOD, remaining
   уменьшен; его historical_operation_id входит в явную полную группу замены.
   Оплаченная часть не должна ещё раз попадать в среднее residual.
6. Идемпотентность импорта — по действующему полному внешнему ключу из
   docs/data-contracts/README.md: компания/счёт + система + внешняя компания + вид
   записи + внешний ID. Идентичный повтор безопасен; иное содержание под тем же
   ключом — конфликт. Новый внутренний UUID не должен обходить это правило.
   Один голый external_operation_id не является глобально уникальным.
7. Обновление/перенос/отмена меняют версии и создают новый снимок/прогноз;
   старый результат остаётся неизменным и помечается stale. Отмена remaining
   не удаляет уже исполненный debit и не «возвращает деньги».

ML сейчас принимает согласованный снимок с разными внутренними UUID и одинаковым
внешним ID. Это не проверка фактического Core importer и не доказательство его
ошибки. Валидация повторного импорта нужна на входе Core; отдельный ML guard
возможен только после согласования полной namespace-семантики, без эвристики по сумме.

## Владельцу API

Auth HTTP API уже вошёл в main через PR30. Финансовая часть ещё требует Core
client/handlers: платежи create/update/match/cancel, CreateForecast/GetForecast,
статусы ожидания/ошибки/stale и повторное чтение результата. Использовать
docs/core/api-adapter.md и rest-rpc-map.json; существующий Auth не обходить.
Браузер/Go API не выбирают ML метод/модель и не вызывают ML напрямую.

Core CreateForecast возвращает durable acceptance, затем GET/polling получает
сохранённый результат. 202 не означает, что расчёт уже завершён. Money в HTTP —
десятичные строки minor units без float/JS Number; null probability не отображается как 0%.

## Демо-часы и частичная оплата после cutoff

Начальные демо-часы **01.10.2026**, accepted EOD **30.09.2026**; на экране явная
подпись «синтетический демо-сценарий». Часы ОС/production не меняются. Известные
платежи синтетические; это не восстановленный исторический календарь из выписки.

При CURRENT на cutoff+1 обязательно no_post_cutoff_movements=true, но **только
если это правда**. Нельзя проставить флаг ради обхода проверки после движения
01.10 при сохранённом EOD30.09. Если частичная оплата произошла 01.10, нужен
новый accepted EOD01.10, согласованная coverage и новый cutoff; демо-часы можно
явно продвинуть до 02.10. В текущем контракте нет intraday bridge.
Не переписывать конфликтующим значением уже принятое наблюдение 30.09.

RPC-fixtures ниже — отдельные синтетические снимки на одной дате cutoff,
каждый с согласованными фактами/EOD. Partial fact в них **уже на 30.09**,
движений после cutoff нет. Это проверка ML-входов, не команды изменения
существующего Ledger/EOD. При настоящем последовательном Core flow с новым
cutoff окно сдвинется: ожидаемые суммы нужно пересчитать на его входе, а не
механически требовать константы из таблицы при другой истории/горизонте.

## Проверенный сценарий единого RPC

Команда из корня checkout с закреплённым Python/RPC окружением и bindings:

```powershell
.venv/Scripts/python.exe -X utf8 -B services/ml/verify_manual_payment_rpc.py `
  --start-local-server `
  --data-dir D:/hack-rnd-2026/hack-rnd-autumn-2026/data/cashflow/raw `
  --output-dir services/ml/artifacts/manual_payment_rpc_replay `
  --main-sha 02ec65c1c136594755c11def50100921551bd8bc
```

Сервис запускается отдельным процессом; получает protobuf, не путь CSV.
Локальный transport insecure только loopback; это не provisioned PKI/Core worker.
Для внешнего стенда скрипт поддерживает --target и mTLS --ca/--certificate/--private-key.
Output обязан быть новым, предыдущие результаты не перезаписываются.

Компания C002, 30 точек. Деньги RUB по соглашению fixture; dataset сам не
сертифицирует валюту/банковскую полноту. UUIDv5 и version counters — fixture,
в Core использовать свои canonical IDs/versions и настоящий доступ к компании.
Сумма выбирается по baseline до будущих фактов, чтобы показать минус на due date.

| Состояние fixture | Изменение | Первый минус | Остаток на конец горизонта |
|---|---|---|---:|
| 0 | Без ручного платежа | нет | 979 295,45 |
| 1 | Добавить 1 309 405,50 на 10.10 | 10.10 | −330 110,05 |
| 2 | Изменить сумму на 1 309 675,50 | 10.10 | −330 380,05 |
| 3 | Перенести на 20.10 | 20.10 | −330 380,05 |
| 4 | Факт частичной оплаты 436 558,50 уже в EOD; remaining 873 117,00; группа замены | 20.10 | −330 380,05 |
| 5 | Отменить только remaining, исполненный факт сохранить | нет | 542 736,95 |

Все 30 дневных остатков каждого состояния совпали с независимым integer
расчётом. Повтор каждого запроса детерминирован, reference verify_response PASS.
Вероятность оставалась недоступной. Наивная частичная оплата без включения
факта в replacement дала лишние **145 519,50** расхода (ровно треть оплаченного).
Дубликат внутреннего ID и CURRENT cutoff+1 без attestation получили INVALID_ARGUMENT.
Новый UUID с тем же внешним ключом принят ML — это отдельный probe для требования Core.

Локальные подробности: ignored artifacts/manual_payment_rpc_v2_publish/summary.json и 12 canonical
request/response JSON. Нет заявления об оценке качества или импорте/SQL/API E2E.
Публикуемый сценарий также проверяется test_rpc_manual_payment.py на искусственных
90 днях без participant dataset: полный lifecycle, повтор, отрицательные ответы,
сохранность исполненного расхода и честное обозначение transport/Core readiness.

## Когда весь обязательный сценарий действительно пройден

- Войти через настоящий разрешённый flow, выбрать доступную компанию и счёт.
- Создать/изменить/перенести платёж из браузера; получить **новый** сохранённый
  финансовый прогноз через API → Core worker → Predict → Core storage → API.
- Подготовить допустимую дату частичного факта/EOD, сопоставить его и remaining;
  доказать отсутствие дополнительного residual-расхода и что отмена не удаляет факт.
- Повторить импорт исходного факта с тем же внешним ключом: нет второй записи,
  второго debit или повышения версии от replay; конфликтующее содержание отвергается.
- После обновления страницы прочитать тот же сохранённый результат и версии;
  старый прогноз не переписан. Неверный company scope и сбой ML не дают fake success.
- Показать loading/error/stale, 30 точек, дату/глубину минуса, происхождение
  ручного платежа, limitation диапазона и отсутствие калиброванной вероятности.

Статус: ML RPC-часть этого сценария проверена; Core/API/storage/full browser
flow **не проверены**. Их готовность подтверждают владельцы соответствующей реализации.
