# Передача Core/API: известная выплата и частичная оплата на демо

24.10.2026; исходный main `ea433ddd222aa7e279245b6bcd164c1687da7db3`.
Подготовлено для согласования и проверки владельцами; автоматически не отправлено.
Код Core/API/frontend, Auth и canonical protobuf этой задачей не менялись.

## Подтверждённый блокер

В `services/core/internal/client/ml/financial.go` функция `encodeFinancial`
отвергает `KnownPayments` и всегда создаёт `CalendarKnowledgeMode.UNAVAILABLE`.
`validateFinancialResponse` требует `HISTORY_ONLY_NO_CALENDAR`, отсутствие
replacement IDs и равные средние потоки во все дни. Поэтому передать только
календарь недостаточно: входной DTO/mapper, проверка ответа и сохранение
результата должны согласованно поддержать финансовый сценарий.

Сам protobuf `ml.v1.ForecastService/Predict` уже содержит `FinancialCalendar`,
`CalendarGroup`, `ScheduledPayment`, components и replacement evidence.
Новый RPC, REST из ML или изменение Auth не нужны.

Финансовый контекст выбирает Core, он фиксируется в job:
`mean_90 / mean_90_components_v1 / calendar_replacement_v1`.
Пустой календарь не разрешает переходить на ограниченный baseline-профиль.

## Минимальная приёмка для владельцев Core/API

1. Сформировать immutable covered snapshot, accepted cutoff EOD, операции и
   календарь согласованных версий. Для CURRENT на cutoff+1 подтвердить отсутствие
   движений после cutoff. Если исполнение произошло позже — принять новый
   EOD/cutoff; не подменять историческую доступность сегодняшними статусами.
2. Новое обязательство передать как подтверждённую дополнительную полную группу;
   для замены регулярного — явные historical operation IDs и полный график
   компонента на весь горизонт. Одной категории/месяца недостаточно.
3. После partial уменьшить remaining, сохранить исполненный факт в Ledger/EOD
   и включить его ID в группу замены. Отмена remaining не удаляет факт.
4. Проверить identity/model/calendar/version echo, 30 дат и точную формулу
   остатка. При CURRENT не требовать предупреждение `HISTORY_ONLY_NO_CALENDAR`
   и пустой replacement. Сохранить новый job/result; старый не переписывать.
5. Проверить из API и браузера: создание, изменение суммы, перенос, partial,
   отмена; после reload читается тот же сохранённый результат. API вызывает Core,
   а не ML напрямую. Импорт replay по полному scoped external key не добавляет
   второй факт. Проверка ML не является проверкой реального Core importer.

## Числовой сценарий без participant dataset

Синтетическая компания соответствует `deploy/stack/seed-demo.py`:
90 покрытых дней, 1 000 ₽ поступлений и 4 000 ₽ расходов ежедневно.
Демо-дата 01.10.2026, cutoff 30.09.2026, accepted EOD 50 000 ₽.

| Снимок | Начальный EOD | Будущий расход на 05.10 | Первый минус | Конец 30 дней |
|---|---:|---:|---|---:|
| A: без календаря | 50 000 ₽ | — | 17.10 | −40 000 ₽ |
| B: обязательство 10 000 ₽ | 50 000 ₽ | 10 000 ₽ | 14.10 | −50 000 ₽ |
| C: из B уже оплачено 3 000 ₽ | 47 000 ₽ | 7 000 ₽ | 14.10 | −50 000 ₽ |

C — отдельный согласованный синтетический снимок с исполнением до/на cutoff,
не команда изменения уже принятой исторической выписки. При реальной оплате
после cutoff даты и EOD нужно продвинуть согласованно.

В C расход горизонта 127 000 ₽; исполненные 3 000 ₽ уже отражены в EOD.
До 05.10 путь C ниже B на 3 000 ₽, с 05.10 пути совпадают. Так проверяется
сохранение суммы обязательства: paid + remaining = 10 000 ₽.
Если оставить remaining 10 000 ₽, обязательство ошибочно становится 13 000 ₽.

## Воспроизведение и доказательства

[Памятка](DEMO_RUNBOOK.md) содержит команды mTLS-сервера и
`verify_demo_company_rpc.py`. Клиент сохраняет canonical request/response JSON
для A/B/C и summary. Артефакты исправленного локального прогона:
`artifacts/demo_mtls_20261024T205040Z/demo_2026-09-30/`.
Эти JSON можно использовать для сопоставления с запросом реального Core;
артефакты не включаются в Git.

На стороне ML также проверен полный lifecycle C002 скриптом main
`verify_manual_payment_rpc.py` через тот же mTLS-сервер. Синтетические будущие
платежи не являются метриками исторической точности модели.

Вероятность остаётся недоступной: `not_calibrated`,
`REQUIREMENT_OPEN_NO_CALIBRATED_GAP_PROBABILITY`. Диапазоны подписываются
«чувствительность сценария, не вероятность». Оценка GBM30 не подключается.

## Что ещё не подтверждено этим прогоном

Настоящий Core worker, API, PostgreSQL, браузер и развёрнутый стенд здесь не
запускались. `deploy/stack/smoke.py` проверяет сохранённый прогноз через API,
но не ввод/partial/cancel платежа и не браузер. Владелец Core/API подтверждает
исправленный сквозной сценарий отдельным результатом; до этого статус — не пройден.
