# REST Frontend ↔ Go API: передача frontend-разработчику

Дата: 2026-10-23. Версия контракта: `0.1.0`.
Источник маршрутов, тел запросов/ответов и ограничений —
[openapi.yaml](openapi.yaml). Это проект контракта **на ревью разработчиком**,
а не готовый API или подтверждение работающих сервисов. Примеры — учебные.
Изменения схем сначала вносятся в OpenAPI; этот файл объясняет пользовательские
сценарии и не заменяет схемы.
REST-пути вида `/companies/…` ниже указаны относительно префикса `/api/v1`.

Контекст: [архитектурный план](../../.agent/plans/cash-flow-architecture.md),
[описание продукта](../../.agent/plans/cash-flow-product.md),
[результаты локальной проверки](../../.agent/references/dataset-profile.md).
Исходный README находится в локальном `dataset/README.md`; публикация датасета
этой поставкой не определяется.

## Страницы и состояния

Маршруты страниц ниже — предлагаемая структура frontend, не REST URL.
Импорт может открываться мастером из «Операции и данные»; план-факт — вкладкой
сохранённого прогноза. Отдельный экран для каждого модального окна не нужен.

| Страница | Предлагаемый маршрут | Содержание |
| --- | --- | --- |
| Вход | `/login` | Email/пароль, ошибки, переходы к регистрации и восстановлению |
| Регистрация | `/register` | Личный аккаунт; компания автоматически не создаётся |
| Подтверждение email | `/verify-email` | Подтверждение, истёкшая ссылка, повторная отправка |
| Запрос восстановления | `/forgot-password` | Запрос письма; одинаковый ответ независимо от существования аккаунта |
| Новый пароль | `/reset-password` | Установка пароля по действующему одноразовому токену |
| Рабочее пространство | `/workspace` | Список компаний, создание компании, входящие приглашения и принятие/отказ |
| Обзор | `/companies/:companyId/dashboard` | Остаток счёта на дату, актуальность, график, предупреждения, ближайшие платежи, запуск прогноза |
| Операции и данные | `/companies/:companyId/transactions` | Операции, фильтры, источник, категории и ручная корректировка категории |
| Импорт | `/companies/:companyId/imports` | Выбор «Файл» / «Внешняя система», проверка, preview, явное применение, ошибки и история загрузок |
| Календарь | `/companies/:companyId/calendar` | Известные будущие поступления/расходы, создание и изменение платежей |
| Прогноз | `/companies/:companyId/forecasts/:forecastId` | Статус, дневной график, разрыв, ограничения качества, причины и рекомендации |
| Сценарии «что если» | `/companies/:companyId/scenarios` | Четыре шаблона, сохранённые сценарии и сравнение с базой; ответное действие на стресс |
| План-факт | Вкладка `/companies/:companyId/forecasts/:forecastId` | Сравнение сохранённого прогноза и появившегося позже факта; неполное покрытие отмечается явно |
| Сотрудники | `/companies/:companyId/members` | Участники и приглашения; управление доступом владельцем |

Основная навигация: «Обзор», «Операции и данные», «Календарь», «Сценарии».
Компания/сотрудники и профиль/выход — отдельные пункты меню.

Для финансовых экранов нужны состояния: нет данных, идёт импорт, требуется
исправление файла, недостаточная/неполная история, выполняется расчёт, расчёт
завершился с ошибкой, результат устарел, сеть недоступна, сессия истекла,
доступ к компании отозван. Недостаток данных не обозначать как «риска нет».
Вероятность `null` показывать как «не оценена», а не как `0%`.

## Вход, компания и права

Владелец выбрал самостоятельное приложение, регистрацию и две роли в компании:
`owner`/`financier`. Приглашается уже зарегистрированный пользователь по известному
email; создание приглашения само по себе не предоставляет доступ.
Рекомендуемая матрица: обе роли работают с финансами, только владелец управляет
компанией/участниками. Сервер проверяет права при каждом запросе, в том числе
polling; скрытая кнопка не обеспечивает защиту. Роль не является глобальной.

Email/password, подтверждение email, cookie-сессия `HttpOnly` и CSRF-защита —
**предлагаемый профиль текущего контракта**, а не новый Accepted ADR.
Frontend использует cookie по настройкам развёртывания и не сохраняет пароль
или идентификатор сессии в `localStorage`. Точный обмен и заголовки описаны
в OpenAPI. Перед любым изменяющим запросом, включая вход/регистрацию,
получает токен через `GET /api/v1/auth/csrf`, затем передаёт его
в `X-CSRF-Token`. После успешного входа запрашивает новый токен, поскольку
сессия ротируется. Профиль предполагает один origin для frontend и Go API.
Токены подтверждения/восстановления не логируются.
Приглашённый финансист принимает приглашение под своим аккаунтом; отдельная
компания или пароль владельца ему не нужны. ИНН компании не доказывает права
на неё и не подключает автоматически банковский счёт.

## Общие правила DTO

- `Money`: величина со знаком в минимальных единицах строкой
  (`amount_minor: "-4000000"`, `currency: "RUB"` = −40 000 ₽), для остатков
  и отклонений. `PositiveMoney` строго больше нуля и используется для движений
  с отдельным направлением; `NonnegativeMoney` допускает ноль, например для
  максимальной нехватки. Не переводить денежные расчёты в дробный JavaScript `number`.
- Деловые даты — `YYYY-MM-DD`; моменты времени — RFC 3339 в UTC с суффиксом `Z`.
  Дату платежа не сдвигать преобразованием в локальный часовой пояс браузера.
- ID непрозрачны. `company_id` в API — внутреннее рабочее пространство;
  `C001` из файла — внешний идентификатор источника, не tenant и не право доступа.
- В `Source` различаются `external_operation_id` фактической операции
  и `external_payment_id` ожидаемого платежа; ID имеют разные пространства,
  не заменяют друг друга и не означают автоматическую оплату обязательства.
  Для ручных записей оба внешних ID равны `null`.
- Списки используют пагинацию и фильтры из OpenAPI; клиент не рассчитывает,
  что загружена вся история, по одной странице результата.
- Ошибки содержат стабильный машинный `code`, безопасный текст и при наличии
  ошибки полей/`request_id`. Структуру брать из общей схемы OpenAPI.
  Ошибка HTTP-запроса и терминальная ошибка фонового задания — разные состояния.
- `currency: RUB` — **предлагаемая конвенция MVP**. Валюты нет в CSV/README
  датасета, поэтому это не установленный факт источника. Нет выбора валют,
  обменных курсов и скрытой конвертации; несовместимый внешний источник
  отклоняется явно после проверки соответствия конвенции.

## Импорт: файл и внешний источник

Без файла ручной ввод использует отдельную датированную запись остатка
(`PUT /companies/{company_id}/account/balance`) и операции
(`POST /companies/{company_id}/transactions`). Остаток не создаёт фиктивную
операцию, а будущий платёж создаётся в `/payments`, не в истории операций.
Эти формы можно разместить внутри «Операции и данные» и календаря.

Файловая ветка работает с конкретным адаптером предоставленного CSV:
UTF-8 с BOM, `;`, даты `YYYY-MM-DD`, точка в десятичной сумме, ИНН строкой.
`amount` всегда положительный; направление берётся из отдельного поля.
Пользователь выбирает компанию и счёт назначения, а затем явно сопоставляет
внешнюю компанию источника. Для MVP — один расчётный счёт, не совокупный остаток
всего бизнеса. Для фактических операций и внешних наблюдений остатков у счёта один
источник: первая принятая ручная операция закрепляет `manual_v1`, первый
применённый внешний импорт операций или остатков — его
`source_system`/`source_company_id`. Импорт только ожидаемых платежей
эту привязку не создаёт.
Привязку показывает `Account.transaction_source`; смешение фактов разных систем
возвращает `409 FACTUAL_SOURCE_CONFLICT`. Смена `C001` на `C002` внутри того же
источника возвращает `409 SOURCE_BINDING_CONFLICT`. Скрытой смены источника нет.
Другие системы могут явно поставлять только ожидаемые платежи. Внешняя
синхронизация требует `record_kinds`: пользователь выбирает `transactions`,
`planned_payments` и/или `balance_observations` по возможностям коннектора.
Для дополнительной системы выбирается только `planned_payments`;
неподдерживаемый набор отклоняется, а не молча обрезается. CSV-адаптер имеет
фиксированный набор `transactions` + `balance_observations`.
Явный ручной остаток остаётся отдельным подтверждённым якорем и не меняет
источник операций. На дату уже принятого остатка выписки подмена ручным
значением даёт конфликт; неизвестные даты молча не заполняются.
Общий `all_operations.csv` и индивидуальные выписки содержат
одну историю: повтор не должен удваивать операции.
Предлагаемый лимит загрузки — 100 MiB и 300 000 строк; общий файл набора
размером около 64 MB помещается. Это пределы проекта REST для согласования,
а не измеренная пропускная способность готового сервиса. Превышение даёт
`413`; скрытый импорт первых строк вместо всего файла не допускается.

Общий поток: выбрать источник → проверить/подготовить данные → увидеть preview
с периодом, счётом, сопоставлением компании, ошибками, предупреждениями и дублями
→ **явно подтвердить применение** → дождаться результата. Preview
показывает выбранные `record_kinds`, текущий `transaction_source` и предполагаемую
первую привязку `would_bind_transaction_source`. Ограничение источника повторно
проверяется атомарно при применении, включая гонку двух первых импортов.
Проверка/preview не изменяет финансовую историю. Если данные компании
изменились до применения, клиент обрабатывает конфликт версии, обновляет preview и получает новое
подтверждение пользователя; не применяет устаревший результат автоматически.
Статусы импорта: `queued` → `processing` → `preview_ready` → `applied`, либо
`failed` до preview. Preview с блокирующими ошибками сохраняется, но
`preview.can_commit` равен `false`. Применение через
`POST /companies/{company_id}/imports/{import_id}/commit` передаёт `version`
ресурса импорта, `expected_data_version` из preview и `acknowledge_warnings`.
При конфликте версии требуется новый preview загрузкой/синхронизацией;
он не пересчитывается и не применяется скрытно. Повтор успешного commit
возвращает ранее применённый результат, не импортирует строки повторно.
Внешняя ветка проходит ту же проверку и применение; frontend не передаёт
произвольный URL для скачивания backend и не хранит секреты интеграций.

Для внешних систем показываются только фактически доступные коннекторы.
`provider_id` и `adapter` берутся из каталога
`GET /companies/{company_id}/external-providers` как непрозрачные значения.
Названия `demo_accounting`/`demo_tax` в примерах обозначают наши тестовые
источники, а не утверждённые DTO ФНС/1С; frontend не зашивает их как
постоянный перечень официальных поставщиков.
ФНС/1С и другие источники пока **не исследованы и не реализованы**. Mock явно
помечается; его данные не выдаются за live-интеграцию, подтверждённые налоговые
обязательства или банковское подключение. По переданному владельцем условию
оценки mock ФНС/другие интеграции могут дать дополнительные баллы; количество
баллов не задано. Наличие записи коннектора в проекте REST этого не реализует.

Предоставленный набор: 150 компаний, 222 420 операций за 2024-10-01–2026-09-30;
11 166 пустых ИНН контрагентов и 583 пустых назначения. README также предупреждает
о пропусках истории, дублях, возвратах и овердрафте. Пустой ИНН не превращается
в ИНН компании; похожие операции автоматически не удаляются. Предупреждения
показываются отдельно от блокирующих ошибок.
Локальная проверка обнаружила 21 пару возможных дублей с разными ID,
99 расхождений сверки дневных остатков и четыре истории короче 90 дней;
это признаки качества, не установленные причины ошибок и не готовая разметка ML.

`balance_eod` — наблюдаемый остаток счёта на конец дня, повторённый в строках
этого дня. Его нельзя суммировать; расхождение с движениями нельзя «чинить»
придуманной операцией. В данных нет готовых категорий и будущих обязательств:
обязательства вводятся вручную/импортируются отдельно, найденная регулярность
остаётся предложением. Пропуск истории не равен нулевому движению.

## Прогноз и сценарии

Создание прогноза принимает задание надёжно и возвращает `202` с ID и адресом
статуса. GET статуса не запускает расчёт. Повтор отправки с тем же ключом
идемпотентности не создаёт дубликат; точная область ключа и конфликт тела —
в OpenAPI. Задание использует сохранённый снимок, а не меняющийся текущий баланс.
Статусы прогноза: `queued`, `running`, `succeeded`, `failed`.

Начальные настройки UI: опрос через 1 секунду после ответа первые 10 секунд,
затем через 3 секунды; один HTTP-запрос ограничить 5 секундами. Это предложения,
не измеренный SLA. Не отправлять пересекающиеся запросы. Сетевой сбой вызывает
ограниченный backoff, а не перевод прогноза в `failed`. После ухода со страницы
polling прекращается, принятое задание продолжает работу. При возвращении
запрашивается тот же ID; для терминального статуса опрос останавливается.
Права проверяются повторно; при отзыве доступа опрос прекращается.

График/предупреждения связаны с выбранным `forecast_id`. Более поздно завершившееся
старое задание не должно подменять новый результат. Показываются версия/дата
входных данных и устаревание. Численный процент прогресса без измеряемых этапов
не выдумывается; длительное ожидание не означает автоматическую отмену.

В готовом ответе показатели находятся в `result.metrics`: `first_gap`,
`max_shortfall`, `minimum_balance`, `closing_balance`, `gap_probability`.
Последнее поле — объект `{value, unavailable_reason}`, не отдельное число:
оценённая вероятность требует причины `null`, неоценённая — `value: null`
с явной причиной. `input.risk_definition: below_zero_eod` означает модельный
остаток на конец дня ниже нуля.
**Порог и трактовка ещё требуют согласования**: отрицательный
баланс в датасете может означать разрешённый овердрафт, а его лимит не дан.
Нельзя выдавать индикатор отрицательного остатка за доказанную невозможность
платежа. Вероятность остаётся `null`, пока нет корректной оценки; причина
недоступности передаётся отдельно.
Дневное `negative_balance_probability` относится к отрицательному остатку
конкретного дня; `result.metrics.gap_probability` — хотя бы к одному такому
событию за весь горизонт. Общий контейнер вероятности не задаёт событие;
его определяет поле. Дневные вероятности нельзя складывать для получения
горизонтальной.

Четыре шаблона: перенос ожидаемого поступления, снижение выручки, разовый расход,
рост постоянных расходов. Сценарий сохраняет исходную базу, снимок/версию модели
и параметры; не изменяет фактические операции и календарь. Условия применяются
к нужному потоку один раз: перенос платежа не создаёт второе поступление.
Для ответного действия сохраняются стрессовые условия: сравниваются **стресс**
и **стресс + действие**, а не исходная база и результат с потерянным стрессом.
Запрос ответного варианта содержит только `name`,
`comparison_parent_scenario_id` и `response_action`; сервер наследует базу
и полный набор стрессовых условий. Frontend не пересылает `base_forecast_id`
или копию `changes`. В `result.effective_occurrences` сервер возвращает части
платежей **после применения стресса**: `effective_occurrence_id`, исходные ID,
дату, `remaining_amount` и признак доступности ответного действия.
`response_action.target` передаёт только выбранный `effective_occurrence_id`;
frontend не воспроизводит финансовые преобразования и не вычисляет
текущую дату/сумму самостоятельно.
Сумма действия ограничена выбранной частью; сервер проверяет её принадлежность
родительскому прогнозу, исходный стресс сохраняется.
Ответное действие не отправляет реальный платёж или заявку в банк.

Историческая демонстрация использует выбранный срез доступной истории без
заглядывания в будущее. Надпись «Остаток счёта на 30.09.2026» корректна для
соответствующей выписки; надпись «денег сейчас» без свежего источника — нет.
В запросе прогноза явно задаются `cutoff_date` и `horizon_days`;
`start_date = cutoff_date + 1 день` вычисляет сервер и возвращает в ответе.
Для выбранного среза требуется принятый остаток на конец именно
этого дня; старый остаток нельзя молча протянуть через неизвестные дни.
При `BALANCE_AS_OF_UNAVAILABLE` предложить выбрать срез с наблюдением либо
внести подтверждённый датированный остаток с ручным происхождением.
План-факт сравнивает сохранённый прогноз с последующим фактом и явно сообщает
о датах, для которых фактических данных пока нет/они неполны.
`409` у чтения ошибок импорта, сравнения прогнозов и план-факта — штатный
ответ при недоступном для операции состоянии/несовместимости; frontend
обрабатывает машинный код общей ошибки, а не считает каждый GET успешным.

## Проверки контракта

Формат файла — [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0.html).
Для структурной проверки из корня репозитория:

```sh
python -m openapi_spec_validator docs/api/openapi.yaml
```

Команда рассчитана на [openapi-spec-validator 0.9.0](https://openapi-spec-validator.readthedocs.io/en/latest/)
в отдельном окружении проверки; библиотека не добавлена в зависимости продукта.
Редакция после исправлений ревью прошла структурную проверку OpenAPI:
53 операции, 98 схем и 858 проверок примеров по JSON Schema. Пройдены
22 базовые проверки и арифметика примера прогноза, а также 72 целевые проверки
исправленных замечаний. В окружении проверки использованы
`openapi-spec-validator 0.9.0`, `jsonschema 4.26.0`, `PyYAML 6.0.3`.
Это проверки сохранённого описания/примеров и выбранных инвариантов контракта,
**не тесты работающего API**, не проверка производительности и не подтверждение
реализации бизнес-правил или ML. После изменения контракта проверки повторяются.

## Следующий шаг и вопросы ревью

Сначала разработчик проверяет и явно одобряет эту поставку REST. **Сразу после
этого следует этап 1A — исследование официальных API/DTO ФНС, 1С и других систем
малого бизнеса** с Context7 и первичными источниками. Ждать реализации сервисов,
всех protobuf или нового датасета для начала исследования не требуется.
Подготовка контракта не означает завершения всего этапа 1, принятия нового ADR
или разрешения начать реализацию следующего этапа.

На ревью остаются RUB-only и отсутствие валюты в источнике, профиль
email/password+cookie, численный порог/семантика разрыва при неизвестном
овердрафте, матрица прав и окончательные численные ограничения импорта/расчёта.
Доступность коннекторов, имена их DTO и реальные способы авторизации
согласуются по результатам этапа 1A. Работающие backend/auth/email/ML и интеграции
этим файлом не заявляются.
