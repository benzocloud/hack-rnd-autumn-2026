# Мок импорта 1С и ФНС

Локальный стенд генерирует XML, преобразует документы в наш
`NormalizedSourceBatchDTO`, сохраняет обязательства и считает их влияние на
дневной денежный план. Для запуска нужны Python 3.9+ и Linux/macOS; внешних
Python-зависимостей у стенда нет. Команды выполняются из корня репозитория.

Каждый исходный XML и `manifest.json` ограничен 2 MiB. Этот входной лимит
не применяется к накопленному локальному `state.json`, отчёту и нормализованным
пакетам: результат нескольких допустимых документов может быть больше.

## Быстрый запуск

```sh
python3 -B -m tools.mock_import run --out /tmp/cashflow-demo
```

Если каталога ещё нет, команда создаёт набор с `seed=42` и срезом `2026-08-31`.
Повтор той же команды импортирует тот же набор без удвоения сумм.
Для нового набора используйте другой каталог:

```sh
python3 -B -m tools.mock_import run --out /tmp/cashflow-demo-other --seed 7 --as-of 2026-09-30
```

Можно сначала создать только входные файлы, затем запустить импорт:

```sh
python3 -B -m tools.mock_import generate --out /tmp/cashflow-input --seed 42 --as-of 2026-08-31
python3 -B -m tools.mock_import run --out /tmp/cashflow-input
```

`generate` требует пустой каталог. Явно заданные `seed`/`as-of` при повторном
`run` должны совпадать с существующим манифестом. Seed определяет устойчивые
ID; суммы фиксированы сценарием, даты платежей сдвигаются относительно среза.
Это воспроизводимый сценарий, а не генератор статистически реалистичных бизнесов.

## Что находится во входном наборе

Все реквизиты, суммы, даты и контрагенты синтетические. Источники внешних
полей и ограничения зафиксированы в
[исследовании форматов](../../.agent/references/external-data-contracts.md)
и [реестре источников](../../.agent/references/external-data-examples/sources.json).

| Файл | Профиль | Что попадает в расчёт по умолчанию |
| --- | --- | --- |
| `receipt.xml` | Этап оплаты заказа клиента ED 1.25 | Поступление 150 000 ₽, срез + 20 дней |
| `rent.xml` | Заявка на расход ED 1.25 | Аренда: 80 000 ₽ всего, 20 000 ₽ оплачено, осталось 60 000 ₽; + 5 дней |
| `supplier.xml` | Заявка на расход ED 1.25 | Поставщик: 60 000 ₽; + 10 дней |
| `payroll.xml` | Заявка на расход ED 1.25 | Демо-выплата зарплаты: 100 000 ₽; + 15 дней |
| `ens.xml` | Предстоящие начисления ЕНС, КНД 1160082, 5.03 | Обязанность 60 000 ₽, зачтено 40 000 ₽, нужно ещё 20 000 ₽; + 28 дней |
| `ens-no-date.xml` | Тот же профиль ЕНС | 5 000 ₽ без срока: `NEEDS_DUE_DATE` |
| `notification.xml` | Уведомление КНД 1110355, 5.03 | 45 000 ₽ без срока: `NEEDS_DUE_DATE` |
| `notification-correction.xml` | Тот же профиль уведомления | −15 000 ₽: `TAX_ADJUSTMENT_REQUIRES_REVIEW` |

`payroll.xml` демонстрирует расходную заявку с назначением «зарплата»;
это не отдельный зарплатный формат 1С. `+28 дней` в справке ЕНС — явно
сгенерированная дата, не правило определения законного срока налога.

**1С:** namespace `http://v8.1c.ru/edi/edi_stnd/EnterpriseData/1.25`, поля
этапов оплаты и заявок соответствуют исследованной схеме. Корни файлов — наши
документные подмножества: полного сообщения обмена, всех обязательных
ссылочных объектов и совместимости с любой конфигурацией здесь нет.

**ЕНС:** используются поля из прочитанного описания формата 5.03. Оригинальная
XSD справки не получена; полная XSD-совместимость не подтверждена.

**Уведомление:** генератор использует поля сохранённой
[XSD 5.03](../../.agent/references/external-data-examples/UT_UVISCHSUMNAL_1_263_00_05_03_01.xsd).
XSD-проверка структуры не подтверждает контрольные соотношения, Schematron,
правильность имени обменного файла, подпись или приём документа ФНС.
В уведомлении нет срока платежа, поэтому оно не создаёт обязательство автоматически.

## Манифест и собственный DTO

`manifest.json` — наш транспортный конверт, не DTO поставщика. Он содержит:

- `demo`, `schema_version`, `seed`, компанию/счёт и строковый ИНН;
- `cutoff_date`, `horizon_days`, валюту и демо-остаток `opening_balance`;
- `documents[]`: `id`, `profile`, относительный `path`, `sha256`,
  `known_as_of_date`, `mandatory`, `record_assumptions`;
- общие пояснения `assumptions`.

Для 1С `record_assumptions` явно задаёт `paid_minor` по ID этапа/заявки.
Для заявки также нужен `date_choice: "approved"`: адаптер выбирает
`УтвержденнаяДатаПлатежа` и проверяет её относительно `КрайнийСрокПлатежа`.
Без этих допущений сумма документа не считается неоплаченным остатком.
В реальной интеграции остатки исполнения нужно получать из соответствующих
данных базы и сверять с фактическими оплатами.

Для ЕНС демо считает `СумЗачтОбяз` уже обеспеченной деньгами частью обязанности:
в будущий банковский отток входит `Сумма − СумЗачтОбяз`.
Зачёт показан отдельно в `tax_evidence`. Сальдо ЕНС не прибавляется к
банковскому остатку. Это явное правило сценария; реальная сверка требует
истории ЕНС и переводов, чтобы не повторить ранее учтённые движения.

Нормализованный результат лежит в `normalized-batches.json` — массив пакетов
по [схеме NormalizedSourceBatchDTO](../data-contracts/normalized-source-batch.schema.json).
В нём заполнены только `planned_payments`; фактические операции и банковские
остатки из этих документов не выдумываются. Пример записи аренды, ID сокращён:

```json
{
  "external_payment_id": "<id заявки>",
  "direction": "outflow",
  "amount": {"amount_minor": "8000000", "currency": "RUB"},
  "remaining_amount": {"amount_minor": "6000000", "currency": "RUB"},
  "scheduled_date": "2026-09-05",
  "counterparty_name": "Учебный контрагент",
  "description": "Аренда: общий платёж 80 000, оплачено 20 000",
  "source_category": null,
  "status": "partially_matched",
  "availability": {
    "known_as_of_date": "2026-08-31",
    "basis": "demo_assumption",
    "evidence_ref": "documents/rent.xml + явные допущения manifest.json"
  }
}
```

Деньги — строки целых копеек; направление задано отдельно. Даты платежей
— `YYYY-MM-DD`. Даты ФНС `ДД.ММ.ГГГГ` переводятся без изменения календарного
дня; местный `dateTime` 1С используется для проверки даты документа относительно
среза. Неизвестная валюта отклоняется без пересчёта. ИНН остаётся строкой,
включая ведущий ноль. XML 1С — UTF-8, ФНС — Windows-1251.

Происхождение пакета отмечено `synthetic_mock`, доступность — `demo_assumption`.
`retrieved_at` — синтетическое время воспроизведения в дату среза;
`artifact_sha256` — хеш текущего файла манифеста. Это не аудит исторического
получения данных. У источника нет банковского счёта: `source_account_id=null`;
привязку к `acc_demo` задаёт стенд, будущий Core должен задавать её явно.
Признак обязательности остаётся в манифесте и отчёте: в согласованной схеме
платежа такого поля нет. Передача этого признака в Core требует отдельного
согласования контракта; стенд не расширяет DTO молча.

## Результаты и правила применения

| Артефакт | Назначение |
| --- | --- |
| `documents/*.xml` | Сохранённые исходные демо-документы |
| `manifest.json` | Профили, хеши, контекст и допущения |
| `normalized-batches.json` | Нормализованные DTO для будущего импортёра |
| `state.json` | Локальное состояние применённых платежей для проверки повторов |
| `report.json` | Результат по каждому документу, обязательства, налоговые свидетельства, дневной план до/после |

Идентичный платёж с тем же ID учитывается один раз. Изменившийся платёж
под прежним ID получает `CONFLICTING_EXTERNAL_ID`: прежняя версия сохраняется,
новая требует сверки. Каждое XML применяется целиком после проверки всех его
строк; другие корректные документы из набора могут примениться независимо.
Ошибки отдельных документов видны в `documents[]` со статусом `requires_review`.
Даже если новый документ отклонён, ранее импортированная версия остаётся в плане.
`before_import` — состояние перед текущим прогоном, поэтому повторный импорт
даёт нулевую дельту, а не повторное сравнение с пустым состоянием.

Это не сверка разных снимков или разных документов об одной обязанности.
Новый ID справки ЕНС не доказывает новую налоговую обязанность; такие снимки
нельзя без сверки добавлять в один набор как независимые расходы. Связанные
уведомления здесь намеренно не импортируются как дополнительные платежи.
Удаление XML/строки из манифеста не отменяет ранее применённый платёж.

Для примера со срезом `2026-08-31`:

- 8 документов → 5 применённых платежей, 3 документа требуют уточнения;
- начальный банковский остаток — 200 000 ₽, поступления — 150 000 ₽,
  будущие расходы — 240 000 ₽;
- первый отрицательный остаток — `2026-09-15`, нехватка 20 000 ₽;
- остаток на `2026-09-30` — 110 000 ₽ вместо 200 000 ₽ без импортированных платежей;
- повторный запуск → 0 новых платежей, 5 уже присутствующих, изменение остатка 0 ₽.

Для каждого дня: `closing_balance = opening_balance + inflow − outflow`.
Рассчитываются 30 дней после среза; манифест позволяет горизонт 30–90 дней.
Просроченные и выходящие за горизонт записи показаны в `outside_horizon`,
без переноса дат. Нулевой остаток исполнения сохраняется как `matched` и
не создаёт будущий отток. План не моделирует внутридневную очередность платежей.
`probability=null`: модель ML не запускается. Успешный запуск CLI возвращает
код 0, включая ожидаемые документы на уточнение; ошибки конверта/ввода — код 2.
Для автоматических прогонов проверяйте также `requires_review` и `documents[]`.

## Локальный HTTP-мок

```sh
python3 -B -m tools.mock_import serve --bundle /tmp/cashflow-demo --port 8765
```

| GET | Ответ |
| --- | --- |
| `/health` или `/` | Признак демо, список профилей и ссылки |
| `/manifest.json` | Манифест набора |
| `/documents/<имя>.xml` | Байты XML, перечисленного в манифесте |
| `/normalized-batches.json` | Пакеты после прогона |
| `/report.json` | Отчёт после прогона |

Пример чтения:

```sh
curl --fail http://127.0.0.1:8765/manifest.json
curl --fail http://127.0.0.1:8765/documents/rent.xml
```

Мок слушает только `127.0.0.1`. Неизвестные пути возвращают 404, документ
с неверным SHA-256 — 409. Файлы состояния не раздаются. Маршруты принадлежат
нашему стенду и не имитируют vendor API, авторизацию или OData 1С.
CLI импортирует файлы напрямую; HTTP отдаёт те же входы будущему клиенту.
Подключения к Go Core/API/ML пока нет.

## Проверки

```sh
python3 -B -m unittest discover -s tests/mock_import -p 'test_*.py' -v
ruff check .
ruff format --check .
git diff --check
```

Ruff 0.17.1 закреплён в `.agent/infra/requirements-dev.txt`.
HTTP-тест требует разрешённых локальных сокетов. Проверяются повторяемость,
повторы/конфликты, точные суммы, частичная оплата, зачёт ЕНС, отсутствие срока,
отрицательная корректировка, компания/счёт, срез, валюта, небезопасный XML,
пути, арифметика и HTTP-раздача. Полная проверка JSON Schema и внешней XSD
возможна отдельно инструментами `jsonschema` и `lxml`; в runtime они не нужны.
