# Данные для моков и расчёта прогноза

Версия: `0.1.0`, 2026-10-23. Статус: **проект для ревью разработчиком**.
Результат текущего поручения — конкретные JSON DTO, схемы и примеры на основе
предоставленного датасета. Принятие нового ADR, реализация импортера, API,
ML и канонических protobuf этим документом не заявляются.

## 1. Какой файл использовать

| Задача | Контракт | Пример |
| --- | --- | --- |
| Написать мок дополнительного источника либо подготовить выход CSV-адаптера | [NormalizedSourceBatchDTO](normalized-source-batch.schema.json) | [Факты из CSV](examples/dataset-C001.sample.batch.json), [мок будущих платежей](examples/planned-payments.mock.batch.json) |
| Передать самодостаточный снимок в расчёт/прототип ML | [ForecastCalculationInputDTO](forecast-calculation-input.schema.json) | [Снимок с учебным календарём](examples/calculation.sample.json) |
| Мокировать браузерный API и готовые результаты | [Существующий OpenAPI](../api/openapi.yaml) | `Transaction`, `Payment`, `Forecast`, `ForecastResult`, `Scenario` и examples этого контракта |

Первый DTO — результат нормализации внешнего формата **до** назначения внутренних
ID и записи в Core. Второй — снимок **после** проверки и применения данных Core.
`ForecastInput` в OpenAPI содержит параметры/идентичность снимка, но не содержит
саму историю операций. Поэтому одного этого объекта для автономного ML-мока мало.

Мок нашего демонстрационного источника может возвращать `NormalizedSourceBatchDTO`
напрямую. Это наш внутренний формат, а не проверенный протокол настоящих ФНС,
1С или банка. Настоящий источник потребует отдельного адаптера своего DTO.
Новые REST-маршруты или изменение текущих тел запросов не предлагаются.

## 3. NormalizedSourceBatchDTO

Один пакет относится к одной внешней компании и одному выбранному счёту.
Внутренние `company_id`/`account_id` задаёт проверенный контекст импорта;
внешний `C001` не создаёт рабочее пространство и не подтверждает права.

| Поле | Назначение |
| --- | --- |
| `schema_version` | Версия нашего нормализованного формата, сейчас `0.1.0` |
| `source` | Пространство внешних ID, внешняя компания, происхождение, валюта/основание её выбора, техническое время чтения, ссылка и хеш файла |
| `record_kinds` | Явно выбранные типы записей: `transactions`, `balance_observations`, `planned_payments` |
| `factual_period` | Запрошенный включительный период фактов; `null` для источника только ожиданий. Не подтверждает полноту покрытия |
| `transactions` | Исполненные операции: внешний ID, дата, направление, положительная сумма, контрагент, назначение и строка источника |
| `balance_observations` | По одному наблюдению EOD на дату; исходные номера строк сохранены |
| `planned_payments` | Отдельные ожидаемые события: внешний ID, общая/оставшаяся сумма, плановая дата, статус и доступность этой версии сведений на дату среза |

Все три массива присутствуют, даже если пусты. Если тип не выбран в
`record_kinds`, его массив обязан быть пуст. Выбранный тип может иметь ноль
найденных записей. Не превращать пустой ответ в удаление ранее принятых данных.
Семантика удалений и инкрементального обмена не входит в v0.1.

`source_account_id: null` означает, что номера счёта нет в исходнике, а не что
история охватывает все счета. `source.data_origin` отделяет предоставленную
синтетическую историю от отдельно написанного мока.

`source_category` — исходная необязательная метка поставщика. Она не становится
внутренним `category_id` без явного сопоставления. У датасета она равна `null`.

### Преобразование CSV

| Исходное поле | Нормализованный результат |
| --- | --- |
| `company_id` | `source.source_company_id` после явного выбора одной компании |
| `operation_id` | `transactions[].external_operation_id` |
| `operation_date` | `transactions[].operation_date` |
| `amount` | `transactions[].amount.amount_minor`, точное умножение десятичной строки на 100 |
| `direction=Поступление` | `direction=inflow` |
| `direction=Списание` | `direction=outflow` |
| `counterparty_inn` | Строка с ведущими нулями; пустая строка превращается в `null` |
| `counterparty_name` | Строка без выдумывания недостающей идентичности |
| `payment_purpose` | Исходная строка, включая `""` |
| `balance_eod` | Один `balance_observations[]` на компанию/счёт/дату, а не часть суммы операции |
| Номер строки CSV | `source_row_number` и `source_row_numbers`, заголовок — строка 1 |
| Отсутствующая валюта | `currency=RUB`, `currency_basis=adapter_assumption` только при принятой конвенции демо |

`990.00` преобразуется в `{"amount_minor":"99000","currency":"RUB"}`.
Денежные операции используют целые минимальные единицы либо Decimal, не float.
Знак движения определяется направлением; остатки могут быть отрицательными.

`all_operations.csv` и `statements/*.csv` — альтернативные упаковки одной
истории. Их нельзя складывать как независимые источники или разделять на
train/test. Хеш в примере относится к полному исходному файлу; сам пример
содержит только строки до обозначенного среза.

### Будущие платежи

`scheduled_date` — плановая дата денежного движения, не автоматически дата
выставления документа. Документ без срока/ожидаемой даты требует уточнения.
`amount` — общая сумма; `remaining_amount` — ещё не исполненная часть.
`external_payment_id` и `external_operation_id` — разные пространства ID.

`availability.known_as_of_date` относится ко **всей версии** сведений, включая
оставшуюся сумму, статус и текущую плановую дату. Нельзя пометить новый остаток
долга старой датой выставления и включить его в исторический прогноз.

- `source_version_history` требует проверяемого происхождения состояния на дату
  среза; `evidence_ref` указывает на соответствующую запись/версию источника.
- `demo_assumption` означает вымышленное условие демонстрации. Оно запрещено
  в снимке `mode=history_backtest`.
- `retrieved_at` — техническое время чтения; оно не заменяет доказательство того,
  когда бизнес знал о будущем платеже.
- Обновлённая сумма остатка из внешней системы согласуется с сопоставлениями
  фактов в Core. Нельзя вычесть уже учтённую оплату второй раз.
- `cancelled`/`matched` не дают будущего движения; прошлый срок не означает оплату.

## 4. ForecastCalculationInputDTO

Этот DTO задаёт вход базового расчёта, не структуру признаков конкретной модели.
Его собирает Core. Одна компания, один счёт, один неизменяемый снимок.

| Поле | Назначение |
| --- | --- |
| `schema_version` | `0.1.0` |
| `mode` | `history_backtest` либо `scenario_demo` |
| `company_id` | Внутренний ID компании; не внешний `C001` |
| `company_profile` | Необязательные сведения из справочника: отрасль, форма, ИНН; либо `null` |
| `input` | Точная копия схемы `ForecastInput` из OpenAPI: срез, горизонт, остаток, счёт, версия данных и контекст модели |
| `history` | Выбранная история операций и наблюдений остатка, диапазон и явная конвенция доступности |
| `known_payments` | Снимки ресурсов `Payment` с происхождением доступности сведений |
| `categories` | Внутренний справочник категорий; `[]`, пока категории не определены |
| `quality_issues` | Подтверждённые предупреждения/ошибки в форме `ImportIssue` |

`Transaction`, `Payment`, `Money`, `BalanceObservation`, `Category`,
`ImportIssue`, `ModelContext` и `ForecastInput` в `$defs` перенесены из
текущего OpenAPI с заменой только локальных ссылок. Это копия для автономного
валидирования примеров, а не второй независимый источник REST-истины.
При изменении OpenAPI эти копии нужно синхронизировать.

`history.operation_availability_policy=operation_date_eod_assumed` — явная
конвенция воспроизведения данного набора: исполненный факт считается доступным
на конец даты операции. В исходниках нет точного времени появления сведений.
Этот профиль нельзя без изменения контракта переносить на произвольные живые
интеграции с иной задержкой данных. `created_at` ресурса — время импорта в нашу
систему, а не доказательство исторической осведомлённости.

`history.absent_day_policy=unknown`: отсутствие строки не превращается в
подтверждённый ноль, а неизвестный остаток не протягивается молча. При подготовке
признаков можно явно создавать дневную сетку с маской пропусков; это отдельная
версионированная процедура модели. Даты наблюдений, значения и предупреждения
сохраняются. Сумма `balance_eod` по операциям не является признаком.

Из справочника компаний исключены итоговые `last_operation_date` и
`operations_count`, вычисленные по всей истории: их нельзя незаметно использовать
как признаки на раннем срезе. Для отрасли/формы отдельно предполагается статичность
профиля; реальная доступность таких атрибутов на прошлую дату не доказана CSV.

Сценарии наследуют этот снимок и контекст модели. Форматы пользовательских
изменений уже есть в `ScenarioChange`/`ResponseAction` OpenAPI. Они не записываются
в историю фактов; отдельный исполняемый ML-контракт сценарного пересчёта пока открыт.

## 5. Семантические проверки сверх JSON Schema

JSON Schema проверяет типы, обязательные поля, enum, формат денег и часть
условий. Следующие проверки должен реализовать принимающий код; одна успешная
валидация схемы их не доказывает:

1. В пакете одна внешняя компания/привязка счёта; права на внутреннюю цель
   проверяет сервер. Повторно проверяется при применении импорта.
2. `record_kinds` согласованы с возможностями адаптера. В MVP один источник
   фактов/внешних остатков; другой источник может дополнять только ожидания.
3. Внешний ключ включает компанию/счёт, систему, внешнюю компанию, вид записи
   и внешний ID. Повтор идентичного содержания безопасен, изменившееся содержание
   под тем же ключом — конфликт. Подозрительно похожие разные ID не удаляются.
4. Даты фактов/наблюдений находятся в выбранном диапазоне; суммы и валюта
   согласованы. В одном пакете на дату один EOD. Конфликт EOD блокирует применение.
5. Для ожидания `0 <= remaining_amount <= amount`; `planned` имеет полный остаток,
   `partially_matched` — строго промежуточный, `matched` — ноль. Отменённый платёж
   не учитывается независимо от суммы остатка.
6. `input.start_date = cutoff_date + 1 день`, `end_date = cutoff_date + horizon_days`;
   диапазон содержит ровно `horizon_days` календарных дней (в REST сейчас 30–90).
7. История и все признаки не используют факты после среза. Версия модели,
   обучение и подбор параметров также обязаны соблюдать срез; JSON с названием
   модели сам по себе не доказывает отсутствие утечки.
8. Требуется принятый EOD именно на `cutoff_date`; он равен `opening_balance`,
   `balance_as_of=cutoff_date`. Ручной якорь допустим только как явное наблюдение
   `source=manual`. Старый EOD через неизвестные дни не переносится.
9. Все ресурсы снимка относятся к `input.account_id`. Внешние ID компании
   не являются tenant ID; неизменяемость снимка и права обеспечиваются Core.
10. Доступность **версии** ожидаемого платежа не позже среза. Демо-календарь
    исключён из исторических метрик, известные и выученные события не дублируются.
11. Разница `EOD(d)-EOD(previous_observed_day)-net_flow(d)` сохраняется как
    предупреждение, а не исправляется вымышленной транзакцией. Это не доказывает
    полноту всех остальных дат.
12. `below_zero_eod` — условие отрицательного дневного остатка. Из-за неизвестного
    лимита овердрафта оно не доказывает невозможность исполнить обязательство.

Для вычисления дневных агрегатов отдельно хранить положительные поступления,
положительные списания, чистый поток и наблюдаемый остаток. Производные признаки
и преобразования фиксируются версией подготовки; исходные факты не переписываются.
ML прогнозирует согласованные неизвестные потоки/неопределённость, Core собирает
остатки и риски. Нельзя просто прибавить календарь к полному прогнозу всех потоков.

## 6. Проверки этой поставки

В текущем окружении проверены две схемы Draft 2020-12, четыре примера (включая
полный локальный снимок C001) и 12 намеренно ошибочных вариантов. Проверялись
JSON Schema с проверкой дат и выбранные семантические инварианты: денежный
формат, состав пакета, остаток ожидания, граница среза, горизонт, якорь остатка,
чужой счёт, второй источник фактов, повтор наблюдения и подмена режима демо.

Компактный `calculation.sample.json` содержит всего три операции и два
наблюдаемых дня. Это пример структуры, не достаточная обучающая история.
Имена и версии модели — заполнители, работающая модель не заявляется.

Дополнительно из C001 собран **локальный** полный вход на 2026-08-31:
1 078 операций, 409 наблюдаемых дней, EOD `144284223` минимальных единиц при
явном допущении RUB. Полная история не добавлена в репозиторий.
Будущие факты в этот вход не входят. Отсутствующие дни будущего периода
потребуют маски покрытия при оценке: наличие входа не доказывает полноту target.

Проверки выполнялись временным скриптом подготовки; production-валидатор,
его полное покрытие, ML-качество и работоспособность сервисов не заявляются.
