# Ограниченный CSV-прогноз: поведение и проверка качества

25.10.2026. Локальный кандидат по ADR-031; не отчёт о выкладке на сайт.

## Продуктовое поведение

При создании прогноза Core сначала использует существующий совместимый proof,
если он есть. Для импортированной истории без proof выбирается отдельный
`mean_90_csv_v1`, preprocessing `csv_observed_operations_v1`. ML не переключает
модель после ошибки старого профиля. Browser не передаёт сертификат полноты.

CSV-профиль требует истории, охватывающей 90 дней до cutoff, принятого EOD
ровно на cutoff, одного импортированного namespace с возможными ручными
дополнениями по ADR-032 и не более 20000 операций в окне. Ручные дополнения
сохраняют своё происхождение и входят в расчёт потоков и reconciliation.
Обнаруженное ненулевое расхождение EOD/движений отклоняется.
Согласованность остатков не доказывает отсутствие пропущенных взаимно
компенсирующих операций: полнота остаётся неизвестной.

Средние поступления/расходы — суммы доступных операций, делённые на 90 дней.
Прогнозные остатки считаются от принятого cutoff EOD. Неизвестные исторические
дни имеют отсутствующие суммы/остатки и source `unavailable`; даты с частью
данных имеют source `partial`. Модель не пишет нулевые факты и не восстанавливает
баланс на неизвестные дни. Неизвестные будущие обязательства не учтены.

API возвращает `history_assessment`, `history_coverage: null`, readiness `limited`
и явные limitations. Вероятность — `not_calibrated`, интервал не оценивается.
UI показывает пояснения на русском. Новое создание прогноза переоценивает уже
загруженную историю; импорт, финансовая revision и старые результаты не меняются.

Отказы различаются: `HISTORY_WINDOW_TOO_SHORT`,
`HISTORY_RECONCILIATION_FAILED`, `HISTORY_SOURCE_UNSUPPORTED`,
`HISTORY_OPERATION_LIMIT_EXCEEDED`, `BALANCE_AS_OF_UNAVAILABLE`.

## Описательная оценка

Протокол `csv_mean90_observed_eod_descriptive_v1`, без fitting и выбора порогов
по результату. Две фиксированные номинальные даты: 31.07.2026 и 31.08.2026.
Для каждой компании cutoff — последняя дата с EOD не позже номинальной даты;
в модель передаются только данные, датированные не позже cutoff. Горизонт 30 дней.
Ошибки считаются только на реально наблюдаемых будущих EOD, без forward-fill
и выдуманной truth для пропущенных дат. Сравнение — постоянный последний EOD.

Исходный набор: 150 файлов `dataset/statements/*.csv`; SHA256 списка
`filename:sha256` в порядке имён:
`b4df8ab401db6c4ed7c960909dbdf55ae1a0e227825d300c48882437d84f8d6e`.

| Измерение | Результат |
| --- | --- |
| Кандидатные окна | 300 |
| Оценённые окна / компании | 248 / 128 |
| Реальные будущие EOD-точки | 4514 |
| Отклонены по расхождениям истории | 24 |
| Короткая история / нет прошлых операций | 12 / 2 |
| Нет наблюдаемого будущего EOD для оценки | 14 |
| MAE CSV-профиля | 123347040.06 коп. = 1233470.40 ₽ |
| MAE постоянного последнего EOD | 113610070.75 коп. = 1136100.71 ₽ |

У CSV-профиля ошибка примерно на 8.6% выше наивного сравнения. Этот результат
не подтверждает преимущество подхода. Окна не объявляются blind holdout,
веса компаний не выравнивались, вероятность не калибровалась. Численных
promotion gates нет. Успешный runtime вызов не считается доказательством
достаточной финансовой точности или закрытием требований ТЗ по вероятности.

Воспроизведение из корня репозитория с RPC Python environment:

```sh
python services/ml/evaluate_csv_profile.py --dataset dataset \
  --output services/ml/artifacts/csv-profile-evaluation.json
```

## Совместимость и порядок возможной выкладки

Новые поля protobuf/OpenAPI аддитивны; старые covered jobs используют schema 1
и прежние decoder/model. CSV assessment/EOD evidence замораживаются в job input
schema 2; результат сохраняет текущую форму денежных точек. Миграция БД не нужна.
Успешная оценка не записывает строку в `core_history_coverage`.

После отдельного разрешения выкладки: сначала ML с поддержкой обоих профилей,
затем API/UI с новой проекцией, затем остановить прежний Core и запустить новый.
Смешанный запуск старого и нового Core workers на одной очереди не допускается:
старый worker не знает schema 2. Новый Core читает schema 1 и 2.

После появления schema 2 jobs нельзя откатить Core на старый decoder и ожидать
совместимость чтения/очереди. Rollback должен сохранять decoder schema 2;
удаление jobs/истории ради отката не предусмотрено. Старые сохранённые результаты
остаются неизменными. Реальная browser/Auth приёмка и публичная выкладка требуют
отдельной проверки; интеграционный HTTP тест использует Auth test double.
