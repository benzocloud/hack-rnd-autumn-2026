# ADR-031 — прогноз по CSV с автоматической оценкой качества

Дата: 25.10.2026, Europe/Moscow.
Статус: **продуктовое поведение принято владельцем** сообщением «согласуй тогда»
после сверки исходного ТЗ и предложения общего файлового пути.
Технический план ниже подготовлен для реализации; код и rollout этим решением
не объявляются выполненными или принятыми.

## Основание

Исходное ТЗ «Прогноз денежных потоков», физические страницы PDF:

- С. 4–5: категоризация, регулярность, известные будущие платежи, ежедневный
  прогноз минимум на 30 дней, дата/сумма/вероятность кассового разрыва.
- С. 8: прототип принимает историю и выдаёт прогноз; необходимы проверка
  качества модели, график и предупреждения.
- С. 9: предусмотрена обработка недостаточных и неполных входных данных.

ТЗ не задаёт обязательные 90 дней входа, банковскую сертификацию или ручное
разрешение каждого файла. Требование 90 дней принадлежит текущему профилю
модели, а allowlist manifest — принятому ранее механизму synthetic demo.

## Принятое продуктовое поведение

1. Любая доступная пользователю компания может загрузить поддерживаемый CSV
   и получить оценку пригодности данных для прогноза без настройки manifest
   оператором для каждого hash/company/account.
2. Система проверяет формат, операции, период, остатки, конфликты и доступные
   признаки пропусков. Решение о возможности расчёта принимает сервер.
3. При пригодных данных пользователь получает прогноз минимум на 30 дней.
   Ограничения входа и качества результата видны рядом с графиком.
4. Отсутствие банковского подтверждения само по себе не блокирует обычный
   CSV-путь. При этом проверка CSV не доказывает полноту банковской истории.
   Такой результат не маркируется как `certified` или разрешённая demo fixture.
5. Если выбранная модель не может корректно обработать данные, интерфейс
   показывает конкретную причину и действие для исправления. Отсутствие
   manifest не заменяется сообщением, что пользователю не хватает 90 дней.
6. Пропущенные дни и расхождения не становятся известными нулевыми движениями
   или выдуманными операциями. Подготовка входа может использовать только явные,
   описанные и проверенные модельные допущения; график фактов сохраняет пропуски.
7. Применимость нового пути распространяется и на уже загруженную историю.
   Пользователю не требуется удалять компанию или дублировать факты.

Чекбокс, объявляющий данные полными, не был согласован как обязательное условие
и этим ADR не вводится. Владелец отдельно подтвердил первый ограниченный профиль:
охват 90 календарных дней, остаток на cutoff, неизвестные дни остаются неизвестными,
обнаруженное расхождение EOD блокирует расчёт. Это выбор текущего профиля,
а не требование ТЗ. Прогноз по более короткой истории требует отдельного профиля.

## Граница с ADR-029/030

ADR-031 отменяет обязательность operator manifest для обычного CSV-прогноза.
ADR-030 продолжает определять отдельный явно включённый dataset fixture mode
и synthetic calendar. Новый путь не получает эти разрешения автоматически.

[ADR-032](032-manual-import-supplements.md) разрешает ручные дополнения после
импорта. CSV-профиль учитывает их вместе с операциями единственного внешнего
namespace, сохраняя provenance и повторно проверяя остатки на новой revision.

Текущий `mean_90_components_v1` по-прежнему требует предусмотренный им вход.
Нельзя передать ему неизвестную историю под существующим coverage kind или
ослабить decoder без версионирования и проверки качества. Нужен явно выбранный
совместимый профиль подготовки/модели. Пока он не реализован и не проверен,
новое продуктовое поведение не считается доступным на сайте.

Вероятность разрыва остаётся требованием ТЗ. Предупреждение о качестве входа
не подтверждает калибровку вероятности; `not_calibrated` не закрывает требование.

## Предлагаемый технический этап D2.3a

Цель: один путь CSV → оценка качества → прогноз для новых и существующих
компаний. Переиспользовать API/Core/ML, PostgreSQL и один private Predict.

- Core хранит результат оценки с account scope, data revision, окном, cutoff,
  provenance, версией правил и конкретными причинами ограничений/отказа.
  Оценка пригодности отделяется от утверждения полноты истории.
- Контракты Core/ML/REST получают явное представление нового режима и его
  ограничений. Точные поля/enum и schema versions фиксируются перед реализацией;
  отсутствующие поля старых записей не включают новый режим автоматически.
- ML получает фактические операции и EOD evidence, маски неизвестных значений
  и только разрешённые допущения. Подготовка входа и модель версионируются;
  выбор профиля принадлежит Core, без скрытого fallback.
- API/UI показывают период, пригодность, ограничения, конкретные действия и
  дату среза. Фактическая история доступна независимо от успешности прогноза.
- Для уже применённого импорта нужна штатная повторная оценка с проверкой
  scope/revision и evidence. Она не повторяет import commit, не пишет факты,
  не создаёт proof через ручной SQL и не меняет старые snapshots/results.
- При изменении фактов оценка проверяется заново; metadata-команды сохраняют
  её только по явно проверенным правилам. Snapshot фиксирует оценку своего входа.

Пути: `proto/{core,ml}/v1/`, `docs/api/openapi.yaml`, Core imports/forecasting
services/repositories/app, ML input/model validation, API mappings и frontend
Imports/ForecastDetail/Dashboard. Auth и сервисные границы остаются прежними.

Выбран первый профиль `mean_90_csv_v1` / `csv_observed_operations_v1`, правила
`csv_history_quality_v1`. Суммы фактически загруженных поступлений/списаний
делятся на 90 календарных дней; результат является ограниченной оценкой по
доступным операциям. В историческом входе нет zero-fill неизвестных дней и
реконструированных остатков под видом фактов. Любая ненулевая разница между
наблюдаемыми EOD и известными движениями блокирует этот профиль; скрытые пропуски
с нулевым итоговым net этим не исключаются. Сохраняется предел 20000 операций.

Успешная оценка и EOD evidence сохраняются с job input schema 2. Отказ на этапе
проверки возвращается конкретным HTTP error без создания forecast job или proof;
отдельный журнал отклонённых оценок в этот срез не добавляется. Старые schema 1
jobs/receipts/coverage не переписываются. Повторная оценка выполняется штатным
созданием нового прогноза, без повторного import commit.

Измеримые promotion gates точности и вероятности ещё не утверждены. Результат
описательной оценки этого профиля зафиксирован в
[отчёте качества](../../docs/core/csv-forecast-quality.md); преимущество над
наивным прогнозом на этой выборке не получено.

## Приёмка

- Новый company/account с CSV, отсутствующим в allowlist, проходит штатный путь
  до прогноза либо получает конкретную подтверждённую причину отказа.
- Текущий C001 повторно оценивается без повторной записи 1131 операций.
- Проверяются короткая и редкая история, подтверждённый пропуск операций,
  конфликт EOD, отсутствующий cutoff anchor, чужой scope и stale revision.
- Отдельно проверяются backward reads и прежний fixture/certified путь;
  provenance/limitations сохраняются в ML input, saved result и REST/UI.
- Качество выбранного профиля проверяется на нескольких компаниях и временных
  окнах; успешный пример C001 не заменяет проверку качества модели.
- Реальный browser/Auth путь: upload → preview → commit → оценка → forecast
  → reload. UI не выдаёт ограниченный результат за гарантированное отсутствие риска.

Тесты и review выполняются после содержательных блоков по общему плану.
Перед независимым review остановиться для переключения модели владельцем.
Публикация, merge и изменение серверной конфигурации требуют отдельного поручения.
