# ADR-027 Приватный Auth и серверное управление доступом

Дата: 24 октября 2026 года. Статус: **Accepted владельцем как основание этапа 3.2 PR #17**.
Владелец 24.10.2026 прямо поручил выполнить следующий этап 3.2 после исправлений
и ревью 3.1. Это основание принятия; агентские отчёты не являлись апрувом.
Готовность API/Core и межкомандная интеграция по-прежнему проверяются отдельно.

Номер 027 выбран после сверки всех доступных `origin/*` refs 24.10.2026:
в параллельной Core-ветке `globalarray/feat/core_foundation` на
`20d2adc0a44be6839ee5fef3351c04ccd746e20f` заняты 024 (UUID),
025 (sqlx/layout) и 026 (feature-local application DTOs). Первоначальный Auth ADR
имел номер 024, затем 026; перенумерация в 027 устраняет коллизию, сохраняя
принятие владельцем основания 3.1/3.2 и отдельный gate перед 3.3. Чужие Core ADR
не переносятся и не заменяются этим решением.

## Контекст

ADR-002/003 определяют HTTP границу браузера и protobuf Core/ML. Отдельный Auth
и две роли уже выбраны владельцем, но канонический Auth protobuf, владение
session/CSRF state, recovery компании и численные сроки ещё нужно закрепить.
Референс выдаёт JWT и не реализует нужный жизненный цикл сессии/приглашений.

## Предлагаемое решение

- Добавить приватный `auth.v1.AuthService` в `proto/auth/v1/`, потребляемый API
  и Core по mTLS с allowlist service identity. Расширить область ADR-003 этим
  контрактом после принятия; bindings остаются в internal/gen каждого модуля.
- Auth владеет пользователями, credentials, consent/evidence, security contexts,
  сессиями, токенами, membership/invitation и долговечными командами/outbox.
  Core владеет Company/BankAccount; SQL/shared tables между сервисами нет.
- Сохранить REST email/password, HttpOnly opaque cookie и серверный CSRF.
  API владеет Origin/cookie/HTTP mapping, Auth — состоянием и атомарной проверкой.
  JWT access/refresh и вход по коду не добавлять. Подтверждение email — challenge
  и шестизначный код с TTL 10 минут; reset — одноразовая ссылка. Доставка —
  Resend HTTP API. Новый Company ID — ненулевой UUIDv7, выданный Auth один раз.
- Синхронизировать login/reset через user lock и credential_version; проверять
  актуальное членство на каждом защищённом Core RPC, без положительного кэша.
- Создание компании выполнять через durable Auth intent и идемпотентный Core
  bootstrap. Auth проверяет durable Core receipt до owner membership commit.
  Не требовать распределённой SQL-транзакции или брокера.
- Сохранить существующий consent-контракт и 7-day/30-day invitation policy;
  уточнить безопасный повтор accept после удаления членства.
- Следовать согласованным Go-правилам `.agent/instructions.md`: PostgreSQL
  lifecycle — `internal/app/postgres`, sqlx с `pgx/stdlib` только как драйвером
  `database/sql`. Сборка владеет `Close`; приватные repository получают готовый
  `*sqlx.DB`/`*sqlx.Tx`. SQL — в `sql/`, embed — в `queries.go`; узкие интерфейсы
  принадлежат потребителям. Миграции выполняет отдельная Goose-команда.

Численные TTL, лимиты, lock order, матрица прав, точные RPC/ошибки, email storage
и выбранные версии описаны в [контракте](../../docs/auth/contract.md).
Это единый нормативный текст для ревью, а не два независимо меняющихся набора правил.

## Последствия и границы

Auth становится обязательной online зависимостью защищённых запросов: outage
даёт недоступность, а не разрешение. Взамен отзыв и reset действуют при следующей
проверке без рассылки кэшей/долгоживущих bearer claims. Дополнительный RPC и
PostgreSQL должны измеряться при реализации; SLA не заявляется без замеров.

Стартовые версии инструментов/библиотек предложены для Auth и не обновляют
чужие модули автоматически. Service certificates, Resend API key, sender, keys и backup/deploy
настраиваются отдельно; настоящий auth/email flow этой поставкой не создан.
Реализация Core UpdateCompany и HTTP middleware остаётся у ответственных по
планам Auth/API. Этап 3.2 разрешён владельцем; переход к 3.3 требует отдельного принятия 3.2.
