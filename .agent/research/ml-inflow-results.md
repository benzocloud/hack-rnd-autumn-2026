Проверка: 2026-10-23 — 2026-10-24. Связанный PR: #15, ветка `god4k1ta/feat/ml_baseline`.

**Продолжение от 2026-10-24:** [исследование ежедневного остатка](ml-balance-results.md)
добавляет разбор всех компаний, отдельное наличие/сумму поступлений, календарь

Новые варианты не прошли продуктовые критерии validation, default сохранён.
Последующее поручение разрешило commit/push ML-продолжения после проверок;
датасет и артефакты остаются локальными. Человеческая разметка подготовлена

## Полученный результат

Новый экспериментальный `seasonal_receipts` улучшил прогноз поступлений против
`mean_90` на validation и поздней диагностике, **но не улучшил общий прогноз
остатка**. Поэтому `run_baseline.py` по умолчанию сохранён; `run_inflow.py`
воспроизводит сравнение и выбирает метод по validation, а не пяти разрывам.

Все 1 232 среза (712 development, 204 validation, 316 evaluation) сохранены.
Два исходных baseline воспроизведены: CSV прогнозов побайтово, метрики точно.
Поздний период уже изучался между гипотезами; это исследование, не независимый
holdout и не доказательство выигрыша на новых банковских данных.

для диагностики. Параметры исходных методов и пригодность окон не менялись.

Первые пять простых вариантов не помогли. После этого проверены три веса
сглаживания 12 недель; первый выбор сделан до просмотра его поздних метрик.
Получив смешанный результат, проверены локальный выбор на прошлых окнах и
годовая сезонность. Всё перечислено, неудачные попытки не скрыты. Поздняя
оценка поэтому имеет исследовательский статус и не использовалась для
подбора параметров сезонного варианта или назначения индивидуальных правил
пяти известным компаниям. Для следующего независимого теста нужны новые данные.

`adaptive_inflow` сравнивает mean_90, mean_28 и robust_12w_50 на максимум трёх
прошлых 28-дневных окнах. Требует минимум два и снижение ошибки на 10%, иначе
возвращается к mean_90. Этот механизм не выбран, несмотря на небольшое улучшение
поздней суммы: validation ухудшился. Его реализация сохранена для воспроизводимости.

## Как работает seasonal_receipts

1. Использует только операции, доступные до cutoff, и заранее фиксированные правила.
   Операционная группа: acquiring/cash/customer/marketplace/agency revenue.
2. Считает средний операционный приход за 90 дней. Сопоставляет те же дни
   с лагом 364 дня; рост recent90/prior90 ограничивает диапазоном 0,5–2.
3. Для будущего дня усредняет пять соответствующих дней недели год назад
   (центральный и +/- 1–2 недели), умножает на рост. Смешивает этот уровень
   с недавним средним 50/50. Это простая сезонная гипотеза, не сложная ML-модель.
4. Все прочие поступления — свои переводы, заем, поддержка владельца, unknown,
   страховка, грант, удержание — добавляет полным компонентом среднего 90 дней.
   Не объявляет их ежегодными продажами. Не гарантирует будущую поддержку
   владельца и не использует её последующее фактическое внесение.
5. При неполной/проблемной годовой истории использует точный fallback mean_90.
   Окно не исключается. Из 1 232 срезов годовые признаки доступны хотя бы на
   части горизонта у 449, полностью — у 445; остальные сохраняют baseline.
6. Расходы — mean_90. Суммы в целых минимальных единицах; точные рациональные
   промежуточные коэффициенты, округление до минимальной единицы один раз в день.
   Остаток последовательно меняется на все прогнозируемые поступления/списания.

Будущее не используется ни для категорий операции, ни для сезонного уровня,
ни для локального выбора. Проверка качества исторических дней выполняется
на дату среза. Полная будущая история нужна только для аудита цели оценки.
Нет валюты/кредитного лимита/внутридневного времени; единица — денежная единица
набора. Простые выходные и годовой лаг не являются календарём праздников.

## Поздний период: все 316 окон у 129 компаний

| Метод | WAPE суммы поступлений | Дневной WAPE поступлений | MAE остатка, ден. ед. | Новые минусы TP/FN/FP |
| --- | ---: | ---: | ---: | --- |
| mean_90 | 22,17% | 104,75% | 1 284 713,94 | 1 / 4 / 14 |
| weekday_8w | **20,28%** | **73,28%** | 1 353 218,11 | 0 / 5 / 18 |
| robust_12w_50 | 23,36% | 101,59% | **1 275 906,32** | 3 / 2 / 26 |
| adaptive_inflow | 22,04% | 106,82% | 1 370 910,48 | 2 / 3 / 20 |
| seasonal_receipts | 21,73% | 89,18% | 1 361 780,71 | 1 / 4 / 18 |

Сезонный вариант относительно mean_90:

- Ошибка суммы поступлений: 22,17% → 21,73%, примерно **на 2,0% ниже относительно**.
- Дневной WAPE: 104,75% → 89,18%, примерно **на 14,9% ниже относительно**.
- Ошибка суммы улучшилась в 183 окнах, ухудшилась в 81, совпала в 52.
  По суммарной WAPE компании: 80 улучшений, 27 ухудшений, 22 совпадения.
- MAE остатка вырос примерно на 6,0%; ложные тревоги 14 → 18. Найден тот же
  один из пяти новых разрывов. **Общего превосходства для продукта не доказано.**
- В validation: WAPE суммы 22,45% → 21,04% (примерно на 6,3% относительно),
  MAE остатка 1 161 029,18 → 1 154 230,24; ложные тревоги 6 → 11.

Поздний weekday_8w остаётся лучше по поступлениям, но хуже исходного mean_90
по остатку и не победил в validation. Нет основания выбирать его по уже
просмотренной поздней цели и называть такой выбор независимым результатом.
Не следует заменять модель остатка только по WAPE входящего потока.

Пять минусов остаются диагностикой, не отдельным критерием оптимизации:
сезонный вариант пропустил оба окна C004, C082 и C124; C089 со срезом
2026-05-26 предсказал первую отрицательную дату 2026-05-31 против факта
2026-05-28. Большое сезонное погашение C082 по-прежнему требует графика долга;
исправление только поступлений его не решает.
