## Одна задача и разделение владения

Доведи реальный финансовый frontend: импорт → операции/остаток → прогноз 30 дней
→ календарь → изменение платежа → новый прогноз → reload. Браузер использует
только Go API; цель — доступные действия и ясное поведение на реальных ответах.
Общий developerMode=mock не доказывает готовность. Онбординг, регистрация и Auth
уже закреплены за другим агентом: не реализуй их и не меняй membership flow.
Сохрани регистрацию с чекбоксами и ссылками на отдельные consent/privacy страницы,
version/digest/stale handling; не вставляй тексты документов в форму.

Агент A подключает payments/calendar backend и владеет REST/RPC контрактами.
Ты владеешь frontend/src финансовых экранов, components/helpers/services/interfaces,
их unit/component tests и необходимыми frontend manifests/config. Всё размещай
под frontend/, npm-команды запускай из frontend/. Агент C владеет новыми
frontend/tests/e2e/financial/** и scripts/financial-e2e/**: эти пути не меняй.
Не меняй services/**, proto/**, docs/api/**, deploy/** и общий план.
Не делай redesign и массовое форматирование. Используй текущие UI-компоненты.

Координатор отдельно заканчивает CSV без manifest, mean_90_csv_v1/schema 2,
ручные дополнения после импорта и POST transactions. Это может ещё отсутствовать
в main: проверь опубликованную зависимость и сохрани её URL/SHA в handoff.
Не дублируй эти правки и не возвращай запрет ручного ввода после импорта.
Кнопка сама по себе недостаточна: проверяй фактический HTTP и повторное чтение.
Известный runtime анализ категорий/регулярности ещё может быть недоступен:
не выдумывай результат в браузере и не отмечай backend-анализ реализованным.

## Непрерывные этапы

1. Сверь каждый нужный API маршрут/DTO с актуальным OpenAPI и backend-кодом.
   Запиши матрицу готовности, опубликуй draft и перечень endpoint blockers.
   Используй существующие contracts/services; не изобретай parallel DTO.
2. Заверши импортный UX: upload/progress → preview → issues paging → выбор
   компании → явное подтверждение warnings → commit → обновлённые операции.
   Stale preview предлагает обновить проверку; не повторяй commit автоматически
   с новым ключом. Сообщения должны отличать короткую историю, неизвестные дни,
   EOD conflict, недоступный cutoff, source conflict и сбой сервиса.
3. Доведи операции: ручное создание после импорта, точные деньги, дата/категория,
   CAS/idempotency/retry без дублей, сохранение введённых полей при ошибке.
   Точный imported duplicate показывай понятной ошибкой сервера. При следующем
   CSV предупреждай, что подтверждение совпадения с manual сохраняет обе записи;
   не обещай автоматическое объединение. Ручной остаток — отдельный датированный
   якорь, не автоматически вычисленный баланс и не заполнение неизвестных дней.
4. Прогноз: queued/running/succeeded/failed/cancelled, bounded polling с abort
   при уходе, reload сохранённого результата, staleness по revision и новый
   расчёт после изменения данных. Только 30 дней. Отсутствующие факты и
   probability/bands не превращай в ноль; unavailable не означает «риска нет».
   CSV limited assessment/limitations показывай рядом с графиком. Не подменяй
   исторический ряд прогнозом и не заполняй неизвестные остатки/дни нулями.
5. Календарь: создать/изменить сумму/дату, list/detail, partial match/unmatch,
   отмена remaining и просмотр match history. Действия зависят от state machine;
   cancelled не предлагает запрещённый unmatch. Match связывает факт, а не
   проводит платёж. Покажи remaining и происхождение; после мутации обнови
   account/resource versions, календарь и staleness. Старый прогноз не перерисовывай
   новым содержимым под прежним ID. Дай явное действие «Рассчитать новый прогноз».
6. Подключи согласованные reconciliation controls к существующим API:
   additional obligation и complete replacement выбираются явно, source IDs и
   completeness не выводятся из похожего текста/категории. Не создавай невидимый
   default, автоматически удваивающий историю. При неподдержанном backend режиме
   покажи конкретное ограничение и сохрани blocker в handoff, не подделывай успех.
7. Доведи приёмку на реальном backend: desktop и узкий экран, доступность кнопок,
   читаемый график/ошибки, сумма/дата/remaining до и после мутаций, reload.
   Затем независимые caveman-review и ponytail-review, исправления и push.

## Контрактная зависимость от агента A

Не жди без работы, пока backend появится. Сначала исправляй независимые формы,
состояния и существующие contract-compatible действия. Отсутствующий handler
оформи точным запросом: method/path, request/response/error, сценарий и source SHA
в своём PR/handoff. Вопросы по бизнес-смыслу не решай фронтовыми эвристиками.
Получив опубликованный backend SHA, используй его в отдельном integration checkout
или согласованной зависимости и проверь настоящий вызов. Не включай backend
коммиты в свой PR без необходимости и не меняй чужую ветку. В отчёте разделяй
готовый UI, contract tests и реально пройденный браузерный путь.
