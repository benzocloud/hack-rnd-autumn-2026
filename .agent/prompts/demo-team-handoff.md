## Go API

```text
Синхронизируй свою рабочую ветку Saldo с актуальным origin/main перед новыми
изменениями и перед PR/push. Сначала git status и git fetch origin: сохрани
незакоммиченную работу, не используй reset --hard/force push, не перезаписывай
чужие изменения. Прочитай AGENTS.md, .agent/instructions.md, .agent/decisions.md,
.agent/plans/demo-integration.md и docs/integration-status.md.

Дедлайн — 25 октября, 12:00 МСК. Ты сам составляешь план API. Сейчас приоритет —
первый реальный проход Frontend → API → Core → ML, затем импорт настоящей
выписки → категории/регулярность → будущий платёж → прогноз 30 дней → график
и предупреждение. Сверь доступные RPC с Core/ML/Auth; назови точные недостающие
методы и минимальные финансовые маршруты. Не ограничивай первую поставку только
полным Auth-флоу. Не обращайся напрямую к БД других сервисов и не доверяй
company/role из браузера. API → Core готовит Core-разработчик: канонический
proto/core/v1 и docs/core/contract.md; Core → ML предоставляет ML-разработчик
в proto/ml/v1. Согласуй потребности, не создавай параллельную версию.
Все 54 REST operationId сведены в docs/core/rest-rpc-map.json; преобразования
описаны в docs/core/api-adapter.md. Генерация: buf.api-core.gen.yaml из корня.
ML RPC один — ForecastService/Predict с явной версией модели (ADR-029); mean_90
пока history-only. Не подменяй им финансовый расчёт при пустом календаре или сбое.
Проверь статус реализации: новый proto ещё не означает работающие handlers.

ADR-028 разрешает только явно включённый изолированный demo-profile Auth:
любой шестизначный email-код при сохранении пароля/сессии/CSRF/company scope.
Режим ещё требуется реализовать с Auth; не подменяй финансовые маршруты моками.
Доставка писем не блокирует финансовый сценарий. Проверяй настоящие upstream
вызовы. Представь короткий план, зависимости и критерий первого прохода;
соблюдай поэтапное ревью, публикацию — по авторизации владельца.
```

## ML

```text
Сначала синхронизируй рабочую ветку Saldo с актуальным origin/main: git status,
git fetch origin, сохранение незакоммиченной работы; без reset --hard/force push
и перезаписи чужих изменений. Прочитай AGENTS.md, .agent/instructions.md,
.agent/decisions.md, .agent/plans/demo-integration.md, docs/integration-status.md.
Повтори синхронизацию перед следующим PR/push.

Дедлайн — 25 октября, 12:00 МСК. Приоритет — подключить готовую модель к реальной
цепочке Frontend → API → Core → ML. Ты отвечаешь за Core → ML protobuf
под proto/ml/v1; API → Core (proto/core/v1) готовим в Go Core. Согласуй данные,
не меняй действующий Auth-контракт. PredictFinancial удалён из черновика;
единственный ML RPC — ForecastService/Predict. Финансовая семантика/группы сверки
описаны в docs/core/financial-ml.md. Неподдерживаемые финансовые параметры должны
отклоняться явно, без fallback на mean_90. Bindings локальные у потребителей.
Сначала передай минимальный совместимый контракт и адаптер работающего inference;
выбери существующую проверенную модель вместо нового длинного исследования.

Вход приходит из Core, не из путей к локальному CSV. Сохрани точные суммы RUB,
категории, регулярность, EOD/cutoff и учёт известных будущих платежей ровно один
раз. Исторические ограничения доступности не подменяй будущими фактами.
Верни минимум 30 дневных точек, объяснимые компоненты и обоснованную оценку
неопределённости. Confidence правил не является вероятностью кассового разрыва;
если вероятность не готова, явно укажи незакрытый пункт ТЗ. Подготовь метрики
выбранной модели на временных срезах без утечки будущего для презентации.
Назови первый работающий RPC и зависимости. Поэтапное ревью сохраняется;
публикация — по авторизации владельца.
```

## Auth

```text
Синхронизируй свою ветку Saldo с актуальным origin/main перед работой и перед
следующим PR/push. Сначала git status/git fetch origin; сохрани свою работу,
без reset --hard/force push и перезаписи чужих изменений. Прочитай AGENTS.md,
.agent/instructions.md, .agent/decisions.md, .agent/plans/demo-integration.md,

Дедлайн — 25 октября, 12:00 МСК. Владельцем согласован ADR-028: сейчас важнее
реальная финансовая интеграция, чем доставка писем и полный расширенный Auth.
Речь о подтверждении email, не о новой MFA/2FA. Реализуй явный изолированный
server-side demo-profile для тестовых аккаунтов: любой код из шести ASCII-цифр
принимается для действующего challenge; сохраняются привязка пользователя,
expiry и acknowledgement VerifyEmail без нового автологина. Default выключен,
strict отвергает неверный код; браузер не может включить demo. Согласуй имя
параметра с API/frontend и покажи в UI явную маркировку режима.

Проверка пароля, серверные сессии, CSRF и права компании остаются настоящими.
Назови минимальные готовые RPC входа/регистрации/сессии/доступа и зависимости
онбординга Core, необходимые API. Доставка email, восстановление и приглашения
сохраняются в цели, но не блокируют первый финансовый проход. Не объявляй
mock-подтверждение реальным владением почтой. Проверь demo/strict и company scope.
Представь короткий этап интеграции; после него результат/проверки и ревью.
```

## Frontend

```text
Перед работой и следующим PR/push синхронизируй свою ветку Saldo с актуальным
origin/main. Сначала git status/git fetch origin, сохрани незакоммиченную работу;
без reset --hard/force push, потери чужих изменений и переименования текущей
ветки. Прочитай AGENTS.md, .agent/instructions.md, .agent/decisions.md,
.agent/plans/demo-integration.md, docs/api/README.md, docs/api/openapi.yaml.

Дедлайн — 25 октября, 12:00 МСК. Приоритет — перевести финансовый путь с общего
mock-адаптера на настоящий Go API: реальный импорт → категории/регулярность →
будущий платёж → прогноз → график/предупреждения. Согласуй доступные маршруты
с API. Общий developerMode=mock подменяет также финансы/ML и не доказывает
интеграцию. Браузер обращается только к API, не напрямую к Core/ML/Auth.

ADR-028 разрешает изолированное demo-подтверждение email любым шестизначным
кодом. Серверный режим ещё требует подключения Auth/API; обозначь его в UI,
не включай обход по пользовательскому запросу. Сессии/CSRF/company scope
сохраняются. Форма не должна блокировать демо из-за ожидания настоящего письма.
Сначала выведи настоящие 30 дневных точек и предупреждение, loading/error/stale
states и polling. История → датированный EOD → прогноз остаются целевым
графиком, но исторического ряда ещё нет в OpenAPI: согласуй с API, не выдумывай
endpoint/остатки и не заполняй пропуски нулями. Интервалы/вероятности только из
ответа модели. Докажи первый работающий путь на backend, затем ревью этапа.
```
