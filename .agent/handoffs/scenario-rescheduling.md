# Receipt delays and expense responses

Owner-approved scenario slice, 2026-10-25. Team access is independent draft PR #58; the owner requested a pause before its formal review to switch models. Do not merge/deploy team access as part of this slice.

Independent scenarios support partial `delay_receipt` on server-issued classified sales or known calendar inflows. Add a moved part on its later date, retaining the original unused balance. A date beyond the original horizon retains an explicit out-of-horizon occurrence, rather than deleting money. Expense responses target a concrete server-issued effective outflow occurrence and require an explicit feasibility condition. They clone the saved parent result, inherit all parent stress, and compare only with that parent's forecast. They cannot supply a replacement base or new stress changes. Partial/chained responses consume only the remaining part; calendar, ledger, account revision and prior projections do not change.

Schema3 stores the computed projection, split occurrence ledger, inherited changes, parent ID, response action and out-of-horizon IDs. Root base_forecast_id still references the original core_forecast_jobs row. Old schema1/2 scenarios and original idempotency digests stay compatible. List SQL selects bounded metadata, not full results/occurrences. No new migration, protobuf generation, ML call or auth change. Older readers cannot consume schema3: recovery must retain a compatible reader.

Frontend adds an optional explicit one-off expense to the delay form. This permits the full delay/stress/response cycle on statement-only companies without inventing calendar obligations. Existing forms retain amount/date/remaining validation and show future parts and feasibility conditions.
