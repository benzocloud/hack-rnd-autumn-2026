# Sales reduction scenarios

Owner-approved second scenario slice, 2026-10-25. Keep team access work independent; manually update Core/API only and skip full CI/release builds.

Existing classified mean_90 CSV analysis profiles expose a versioned `classified_sales_mean_90_v1` daily sales target. Plain CSV uses classified sales inflows from the original frozen 90-day window, divided by 90 with the model's half-up rounding. Explicit manual sales categories override rule labels. For CSV+CURRENT calendar, reuse saved `mean_90_uncovered` sales contributions after the model's existing replacement allocation; never reconstruct or reduce known calendar payments. Loans, owner funding, own transfers, refunds, unclassified inflows and outflows do not become sales targets. Classification remains a heuristic, not a completeness certificate or measured sales accuracy. No eligible classified sales means the template stays unavailable.

`reduce_sales` accepts scoped component/occurrence pairs, 1–10000 basis points, selected dates inside the original horizon, and a selected subset of daily targets. Targets outside the selected period remain unchanged. Unknown targets, duplicates, overlapping changes, invalid dates/percentages and overflow are rejected. Reductions round half-up per selected daily target in kopecks; subsequent balances include the cumulative loss. Expense and sales changes can be combined without rewriting facts or the base result.

New reductions persist schema2 with both the calculated result and remaining sales basis; reads do not rerun the reduction. Existing schema1 expenses and their old idempotency digests remain readable/replayable. The list projection includes only change metadata, avoiding loading full results for every list row. No SQL schema migration, protobuf regeneration, ML call, frontend build or financial revision increment is required. Once schema2 records exist, an older schema1-only application cannot read them: recover with a compatible reader rather than deleting user scenarios or blindly rolling the code back.

Focused proof: exclusion of financing/transfers/refunds/unknown inflows, manual category priority, calendar residual selection, period/subset application, one-kopeck rounding, overlap/target/overflow rejection, immutable base/basis, four concurrent PostgreSQL creates with the same key, restart reads, schema1 compatibility, unchanged account revision, strict REST shape and percentages. Core/API module lint and Linux/amd64 builds are checked. Production acceptance uses the owned C900 company, compares all 30 daily deltas and the saved comparison, retries the same key and verifies unchanged source economics and old expense scenarios.
