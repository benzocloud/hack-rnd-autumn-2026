# Паспорт датасета денежных потоков

Проверка: 2026-10-23, локальный каталог `dataset/`. Это проверка предоставленных
файлов и их README, а не оценка качества ML, реализация импортера или ответ
эксперта. Файлы датасета не изменялись. При замене файлов результаты пересчитать.

## Источники и формат

- `dataset/README.md` — семантика полей и описание синтетической генерации.
- `dataset/companies.csv` — 150 компаний; поля `company_id`, `company_name`,
  `company_inn`, `legal_form`, `industry`, `first_operation_date`,
  `last_operation_date`, `operations_count`.
- `dataset/all_operations.csv` — 222 420 операций с 2024-10-01 по 2026-09-30.
- `dataset/statements/C001.csv` … `C150.csv` — те же операции по компаниям.
  Мультимножества всех девяти полей полностью совпадают; это альтернативные
  упаковки одной истории, а не независимые наборы для добавления/тестирования.

Формат: CSV, UTF-8 с BOM, `;`, даты `YYYY-MM-DD`, десятичные суммы с точкой.
Поля операции: `company_id`, `operation_id`, `operation_date`, `amount`,
`direction`, `counterparty_inn`, `counterparty_name`, `payment_purpose`,
`balance_eod`. `amount` положителен; направление задают `Поступление`/`Списание`.
ИНН — строки, сохраняющие ведущие нули. В REST направление нормализуется
адаптером; денежные величины преобразуются точно в минимальные единицы.

SHA-256 для повторной проверки:

```text

companies.csv      0669f211a241ce6e38bb0fd373ea1d84a5a17cfab3833741662382c0669c2cd6
```

## Подтверждённые свойства и ограничения

| Наблюдение | Следствие для продукта и импортера |
| --- | --- |
| README описывает один счёт в одном банке на компанию; номера счёта в CSV нет | Привязать набор к внутреннему счёту компании явно. Это не консолидированный остаток бизнеса |
| Валюты нет ни в колонках, ни в явной конвенции README | RUB — принятое владельцем правило нашего адаптера/MVP (ADR-022), не факт датасета. Не распознавать валюту по ИНН или тексту |
| Нет категорий, налогового режима, календаря будущих платежей, кредитных лимитов и разметки риска | Категории/регулярность оценивать с отдельной проверкой; будущие обязательства вводить вручную/получать из внешнего источника; не обещать налоговый расчёт |
| Нет времени появления/изменения сведений, только дата операции | Историческая проверка требует явной конвенции доступности; реконструированные по будущему события не выдавать за известные на дату прогноза |
| Все `operation_id` уникальны в этом наборе; полных дублей строк нет | Для идемпотентности хранить внешний ID в области источника, привязки счёта и компании; совпадение в новом файле не даёт права перезаписать отличающийся факт |
| 21 пара строк совпадает по всем полям, кроме `operation_id` | Предупреждать о возможном дубле, сохранять обе до подтверждённого решения; совпадение содержимого само по себе не доказывает ошибку |
| 11 166 пустых ИНН контрагентов, 583 пустых назначения | Допускать отсутствие этих значений и показывать предупреждения; не терять строку/не выдумывать значение |

`company_id=C001` — внешний идентификатор синтетического набора, не ID арендатора
платформы и не доказательство доступа. В пользовательском импорте выбирается одна
внешняя компания и явная привязка к разрешённой внутренней компании/счёту.
Общий файл не создаёт автоматически 150 рабочих пространств и членства в них.

`balance_eod` — наблюдаемый остаток на конец дня; одинаков у всех операций дня.
Не суммировать его по строкам. Для первого дня начальный остаток восстанавливается
как `balance_eod − поступления + списания`; это выведенная величина с отдельным
происхождением, а не независимая проверка полноты истории.

Проверены 54 962 наблюдаемых дня. Для 54 812 переходов между последовательными
наблюдаемыми днями одной компании посчитан остаток сверки:
`balance_eod(d) − balance_eod(previous_observed_day) − net_flow(d)`.
Ненулевых расхождений — 99: у 44 модуль ровно 0,01, у 55 — больше 0,01.
Это сигнал проверки качества, а не доказательство причины: README предупреждает
о пропусках истории; возможные округления отдельно не подтверждены.
Не закрывать разницу вымышленной операцией, не перезаписывать исходный остаток.
Хранить наблюдаемый остаток, вычисленное движение, разницу и предупреждение.

## Требования к историческому демо и оценке

- Показывать дату исторического среза и остаток конкретного загруженного счёта,
  а не «деньги сейчас». Фактическая история заканчивается 2026-09-30; для оценки
  30-дневного прогноза нужен более ранний срез с доступным последующим фактом.
- Делить по времени; обучение, категоризация, обнаружение регулярности,
  нормализация, подбор параметров и модельный артефакт не используют будущее
  относительно среза. Сводный файл и выписки не разводить как разные train/test.
- Не восстанавливать известный календарь на дату среза по платежам после неё.
  Отдельно оценивать прогноз из истории и демонстрационный календарь с явными
  допущениями. Пропущенный день не равен доказанному нулю операций.
- Сравнивать с простым базовым подходом, отдельно показывать короткие истории,
  предупреждения качества и доступное покрытие горизонта. Метрики не рассчитаны.
- README допускает овердрафт. Отрицательный прогнозируемый остаток — модельный
  дефицит относительно выбранного порога, не доказательство невозможности
  исполнить платёж без знания лимита. Порог/правило риска и проверка вероятности
  остаются решениями для согласования; дневная модель не гарантирует
  внутридневную платёжеспособность.
