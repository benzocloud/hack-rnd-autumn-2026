# Ветки и оформление коммитов

Источник: `.agent/instructions.md` проекта `references/maxhack`, раздел
«Ветки, коммиты и push», проверен 2026-10-22. Исходный HEAD:
`06e680152ea6b62ea023551498018d7e7b08d877`; файл инструкций без локальных правок.
Это адаптация для этого репозитория: правила названий веток здесь уже определены.

## Сообщения коммитов

Формат: `<type>: <short English summary>`.

По уточнению разработчика сообщения коммитов — заголовок и тело, если оно есть —
пишутся только на английском языке. Это правило текущего проекта.

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `feat` | Новая прикладная возможность | `feat: add analysis result endpoint` |
| `fix` | Исправление ошибки поведения | `fix: handle an empty ML service response` |
| `chore` | Инфраструктура, настройки, документация, планы и служебные изменения | `chore: configure agent runner and planning workflows` |

Использовать `feat`, `fix` или `chore`, выбирая тип по результату изменения.
Не подменять описание заглушкой вроде `update` или `changes`. Заголовок должен
объяснять, что изменилось; разные задачи не объединять ради одного коммита.
Для созданного агентом плана: `chore: update Issue fix plan (request N)`.
Префиксы PR `ML:`, `INFRA:`, `INFRA/ML:` управляют скоупом/skills (ADR-012)
и не добавляются перед типом коммита.

## Ветки и публикация

В maxhack использовалось `<nickname>/<type>/<short_description>`. Этот шаблон
сохранён как источник, но здесь действует текущий префикс `codex/`; существующие
ветки не переименовывать. Автоматическая ветка плана остаётся
`codex/issue-N-plan` (ADR-013). Не выдумывать nickname, remote или базовую ветку;
проверять новое имя через `git check-ref-format --branch`.

Перед коммитом проверить итоговый diff, новые файлы и состав индекса; включать
только согласованный результат и не затрагивать чужую незавершённую работу.
Commit/push — после явного апрува предъявленного результата согласно п. 5
`.agent/instructions.md`. Команды `/create-plan` и `/discuss-plan` уже дают
разрешение на соответствующие плановые коммиты/ветку/PR; отдельное подтверждение
для каждого такого запуска не требуется.

Апрув разрешает согласованный commit/push, но не merge в main или deployment.
Push обычный, без force; после него проверить upstream и соответствие remote
ожидаемому SHA, сообщить ветку и commit. Изменившийся после апрува результат
нужно предъявить разработчику повторно. Эти правила дополняют существующее
управление публикацией, а не включают автоматическую публикацию локальных правок.
