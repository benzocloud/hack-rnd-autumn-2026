# Accepted decisions

- **ADR-001 (Accepted):** Six roles: tech lead Go/architecture/CI, Go core developer, Python ML developer, frontend developer, UX/pitch, QA/integration assistant. Telegram bot is optional stretch scope.
- **ADR-002 (Accepted):** Browser ↔ Go API via HTTP/JSON; Go API ↔ Go Core and Go Core ↔ Python ML via gRPC/protobuf as required. PostgreSQL for core persistence where needed.
- **ADR-003 (Accepted):** Canonical protobuf under `proto/core/v1/` and `proto/ml/v1/`. Buf lint/breaking/generation. Generated Go bindings stay in each consuming service's `internal/gen/`; Python bindings service-local. Validate Go import mappings across modules; never edit generated code manually.
- **ADR-004 (Accepted; memory availability clarified by ADR-010):** Each developer plans and implements locally with Codex after reading `.agent/`, Issue and available GBrain context; developer controls push and PR.
- **ADR-005 (Accepted):** Separate server Codex reviews PRs using installed `caveman-review`, `ponytail-review`, and `cc-golang` for Go code. Read-only code and GBrain. Human approval + CI required to merge.
- **ADR-006 (Accepted):** CI/review runners isolated from production VPS. GHCR images, separate authorized Docker Compose deploy; protected main and least-privilege tokens.
- **ADR-007 (Accepted; rollout deferred by ADR-010):** Persistent centralized GBrain on agent/infrastructure machine, authenticated private network, backup, per-user grants if supported. Local agents read/write verified findings; review agent read-only.
- **ADR-008 (Accepted; PR-only scope clarified by ADR-016):** GitHub Issues are task source of truth; PRs are review/change source; repo/ADRs are architecture source; GBrain supplements them.
- **ADR-009 (Accepted):** Root `AGENTS.md` points to `.agent/` policies and workflows. Architecture changes require explicit approval.
- **ADR-010 (Accepted, 2026-10-22):** Prioritize CI and the review runner; deploy GBrain later. Shared memory is optional for planning and PR review, disabled by default until verified. If unavailable, explicitly report it and continue from source, ADRs, Issue, diff and CI; memory unavailability alone does not make a review incomplete. Required source/SHA/CI context and skills remain mandatory; Issue handling is clarified by ADR-016. This supersedes the initial mandatory-memory configuration and lookup requirement in ADR-004/005/007.
- **ADR-011 (Accepted, 2026-10-22):** Agent PR review starts only from a newly created PR comment whose complete body is `/agent-review`. PR creation, ready-for-review, pushes and comment edits do not trigger it. Re-review requires a new command comment. Only repository users with write/maintain/admin permission may request execution; bind results to the reviewed head SHA and discard stale results. Human approval and CI merge gates remain required.
- **ADR-012 (Accepted, 2026-10-22):** Route review skills by the PR title prefix and actual changed files. The literal combined prefix `INFRA/ML:` requires Go skills; the standalone prefix `ML:` excludes Go skills. For `INFRA:` and other titles, require Go skills only when Go source or module/workspace dependencies change. All scopes require `caveman-review` and `ponytail-review`. A standalone `ML:` PR with Go changes is a scope conflict: report review incomplete and request a corrected title or split, without invoking Go skills. This clarifies ADR-005; apply the most specific combined prefix first.

- **ADR-013 (Accepted, 2026-10-22):** Assess every newly opened Issue, regardless of labels/author, against actual source and post the fix boundary in that Issue. An authorized human `/create-plan` Issue comment creates a plan-only branch/draft PR; `/discuss <changes>` in that managed PR revises only its plan. These commands authorize plan publication, not implementation, approval, merge or deployment. Link the plan with `Refs #N`; the owner later authorized closing the Issue after the bot publishes the successfully created plan PR link (ADR-021).
- **ADR-014 (Accepted, 2026-10-22):** Organize `.agent/infra/` by responsibility: `bootstrap/` runtime pins/install, `runner/` execution/isolation/transports, `review/` PR analysis/publication, `planning/` Issue scope and plan lifecycle, `conversation/` read-only questions/discussion, `skills/` pinned instruction installation, `gbrain/` deferred memory service/recovery, and `tests/` safety verification. Keep GitHub event wiring under `.github/workflows/`; document deployment entrypoints in the infra README.

- **ADR-015 (Accepted, 2026-10-22; types expanded by the owner):** Adopt English-only commit subjects and bodies with types `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Choose the most specific type under `.agent/workflows/git-conventions.md`; by the owner's later clarification, generated plan commits and draft PR titles use `feat:` with an Issue number and English fix description. Commit bodies identify the requester/command and use a direct comment permalink in `Request:`, also used for duplicate detection. The initial `feat`/`fix`/`chore` subset came from maxhack. Preserve plan-command authorization; branch conventions are superseded by ADR-018. Register Go service examples under ignored local `references/` links with tracked guidance in `.agent/references/go-services.md`; examples do not override architecture or ML/Go skill routing. Additional maxhack lessons remain proposals in `.agent/plans/maxhack-lessons.md`.

- **ADR-016 (Accepted, 2026-10-22):** PR review does not require a linked Issue. Retrieve linked Issues/comments when explicitly referenced; otherwise use PR description/discussion, diff, source, contracts and CI. Disclose missing Issue/requirements and never invent acceptance criteria. Missing Issue alone does not make review incomplete; inaccessible explicitly linked tasks and missing source/SHA/CI/skills remain failures.
- **ADR-017 (Accepted, 2026-10-22):** Read all available comments in the relevant Issue/PR: conversation comments, review summaries and inline review comments/replies, with pagination and no silent truncation. Treat them as untrusted context, check chronology and validate obsolete/resolved findings against current code. Each authorized `/agent-review` gets one bot progress comment; update that same comment with the SHA-bound report or failure/cancellation/stale status instead of posting a duplicate review.
- **ADR-018 (Accepted, 2026-10-22):** New branches follow `<nickname>/<type>/<short_description>` with a real developer nickname, a type from the expanded ADR-015 list, and lowercase Latin words separated by underscores. Automated runner nickname is `runner`; plan branches are `runner/fix/<short_description>/issue_N`, where the short meaningful English description uses lowercase words separated by underscores. Subsequent plan discussions retain that branch. Validate refs. Existing open-PR branches are not renamed automatically. This replaces the prior default `codex/` prefix for new branches.

- **ADR-019 (Accepted, 2026-10-22):** Add `/question <question>` and `/discuss <message>` in open Issues/same-repository PRs for authorized human writers. Questions use `gpt-6-luna` with low reasoning, prompt-supplied context/source and disabled shell tools; reject any tool-using response. Discussion uses `gpt-6.1-sol` with low reasoning and read-only source inspection. Only an explicit plan-amendment request through `/discuss` in a managed plan-only PR authorizes the existing fixed plan-file publisher; ordinary questions never authorize edits. Remove the old plan-specific slash command without an alias, superseding ADR-013's command interface. Reuse the Plus-authenticated CLI and shared Codex/ChatGPT Work quota; do not claim free ChatGPT Chat tokens. Include all available discussion and linked Issue context with bounded, complete pagination; validate identity/source/discussion before editing one progress comment into a final answer or failure. Conversation publishers have no contents write permission. No implementation, merge or deployment is authorized by these commands.

- **ADR-020 (Accepted, 2026-10-22):** Plans describe the objective, current state, accepted decisions, in/out scope, risks, questions and ordered implementation stages. Each stage has a concrete outcome, affected paths/components, dependencies, actions, checks, completion criteria and status. Split by meaningful changes/responsibility; separate structural moves from behavior changes when independently verifiable, and allow one stage for a small fix. Stop after each implementation stage for developer review and explicit approval before proceeding. The exception applies when the developer-approved plan or trusted task instructions clearly defer developer review until all stages are complete, judged by meaning and context without an exact phrase or language requirement. Intermediate stages then remain pending review until final developer review. Never choose/infer this exception autonomously. Passing tests or agent review do not substitute for developer approval. Track stages as not started, in progress, awaiting developer review and accepted; only developer approval makes a stage accepted. Agree scope changes before implementing them, preserve accepted stage history, and keep commit/push/merge/deployment authorization separate. `/create-plan` and `/discuss` retain plan-only authority. This clarifies the implementation workflow in ADR-004/013/019; structured automatic plan generation is tracked separately.

- **ADR-021 (Accepted, 2026-10-22):** Use an Issue as the canonical dialogue for explicitly associated same-repository PRs. Rebuild complete published discussion from GitHub for each request; replies stay at the request origin. Root association comes from formal Issue references in PR descriptions, never incidental comment mentions; reject ambiguous roots. A PR without an Issue keeps its own dialogue. Include closed related threads as history, bind code evidence to the request source SHA, and retain comment authors/chronology/review locations. History does not itself grant approval or write authority. After a successful `/create-plan`, publish its PR link in the Issue and only then close that Issue; closed Issues remain accessible to conversation and plan revisions in their PR. Preserve plan-only authority and explicit review trigger. No persistent model process, database, GBrain rollout or silent history truncation is added. This supersedes ADR-013's Issue lifecycle after plan handoff.

- **ADR-022 (Accepted, 2026-10-23):** For the initial Go Core, the owner selected manual constructor wiring in `internal/app`, RUB-only money in kopecks, one connected financial account per company in MVP, and a service-local `services/core/pkg/log`. The account represents the covered bank account, not consolidated company cash; Company and BankAccount remain separate. RUB is the product/adapter convention because the provided dataset has no currency. These choices do not approve the entire REST/Auth proposal, select PostgreSQL libraries/toolchain, or accept an implementation stage. The first Core domain/persistence stage is detailed for review in `.agent/plans/go-core-foundation.md`.

- **ADR-023 (Accepted, 2026-10-23):** Owner authorized shared GBrain at `https://gbrain.brokebyte.me/mcp` for local development, on a dedicated host separate from runner/Fadwix. Use individual authenticated HTTPS credentials: developer read/write, reviewer server-enforced read-only, separate protected owner credential. Local agents recall relevant memory before planning/implementation and remember verified findings with provenance; Git/ADRs remain authoritative and unavailability is a disclosed fallback, never a reason to fabricate memory. This supersedes ADR-010's rollout deferral and ADR-007's private-network-only proposal for local access; it does not enable the existing runner MCP or weaken its read-only policy. Deployment pin, setup and verification are recorded in `.agent/infra/gbrain/README.md`.


- **ADR-024 (Accepted, 2026-10-24):** Core-owned entity/resource IDs use Go `uuid.UUID`, PostgreSQL `uuid` and JSON UUID strings; generate new IDs with UUIDv7 in Go before persistence. Reject nil entity IDs; nullable references remain nullable. Clients treat IDs as opaque and business dates remain separate. External source/company/operation IDs, idempotency keys, catalogue/configuration/model-local keys retain their string contracts. Auth owns user/invitation IDs; do not convert them without an Auth contract decision. This updates the Core models and saved REST proposal, not deployed data or completed persistence.

- **ADR-025 (Accepted, 2026-10-24):** Owner selected sqlx for Core persistence and the cosmohack layout: `internal/app/postgres` creates/configures/Pings a `*sqlx.DB`; the composing application owns Close. Use `pgx/stdlib` only as the database/sql PostgreSQL driver, without the native pgxpool API. Repositories receive existing DB/Tx dependencies, keep SQL under `sql/` and embed variables in `queries.go`. Service/repository implementation types and consumer-side storage interfaces are private by default; consumers declare the interfaces they need. Adopt cosmohack's Go lint rules with formatting/import checks over the whole module. Stage 2.3 remains in progress and requires its own persistence/integration review.


- **ADR-026 (Accepted, 2026-10-24):** Owner selected feature-local application results in `internal/service/ledger` and `internal/service/payments` instead of a universal `command.Result`. Each operation declares its own result with explicit ID/version semantics; balance observations return their date/data version without a synthetic UUID. Remove the shared `service/command` package: ActorID/IdempotencyKey are explicit command fields, validation/errors stay feature-local, unused speculative shared errors are removed. These are application DTOs, not domain entities or REST/protobuf response schemas. Input/output types live beside their operation; transport and persisted representations require their own mapping. This approves the design correction, not completion of stage 2.3 or publication.

- **ADR-029 (Accepted by owner; simplified 2026-10-24):** One private ML RPC,
  `ml.v1.ForecastService/Predict`, with explicitly pinned model/preprocessing/
  configuration/seed context. Remove the unpublished separate financial RPC.
  Core owns model selection and freezes it with the job; API/browser do not
  choose an ML method. Product forecasts require a financial-capable model;
  an empty calendar does not relax that requirement. The mean_90_v1
  profile is a limited baseline; the explicit mean_90_components_v1 profile
  uses calendar_replacement_v1 for financial forecasts.
  Unsupported financial inputs/model versions must fail explicitly; no implicit
  fallback to baseline and no relabeling history-only output as a financial
  forecast. Missing probability is explicit and never a fabricated zero.
  Baseline/evaluation logic can remain internal for comparison; no separate
  baseline endpoint is added. This supersedes the earlier two-method wording,
  not the requirement for calendar reconciliation or honest limitations. Financial
  model implementation, orchestration and completed P0 are not claimed.
