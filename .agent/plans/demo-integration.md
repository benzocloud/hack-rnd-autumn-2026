## Подтверждение в демо — ADR-028

Это подтверждение email, а не полноценная MFA/2FA. Для изолированного демо
с тестовыми аккаунтами допускается любой код из шести ASCII-цифр независимо
от совпадения с отправленным кодом. Настоящая доставка email и строгая проверка
секрета отложены из критического пути сдачи, но сохраняются в целевом Auth.

- Режим включается явно на сервере Auth, по умолчанию выключен. Браузер/запрос
  не выбирает режим. Имя параметра согласует разработчик Auth; server flag
  ещё не реализован/не проверен. В UI явно указано «Демо: подтверждение замокано».
- Сохраняются действующий challenge, привязка к пользователю и expiry. Нельзя
  получить чужую сессию или членство по произвольному email/ID. VerifyEmail
  возвращает acknowledgement; затем обычный вход, без нового автологина.
- Проверка пароля при реальном входе, серверные сессии, CSRF и company scope
  остаются. Обычный режим строго отвергает неверный код. Mock не доказывает
  реальное владение почтой и не включается для настоящих пользовательских данных.
- Frontend-mock уже принимает первый произвольный шестизначный код. Это не
  реализация режима в настоящем Auth. Дополнительный mock-экран кода входа
  не вводит новый обязательный VerifyLogin/MFA RPC в целевой контракт.
- Для проверки интеграции нельзя включать общий frontend `developerMode=mock`:
  он подменяет также импорт/финансы/ML. Финансы идут через API → Core → ML.

## Приоритеты

P0: импорт реального файла, категоризация, регулярность, известные будущие
счета/налоги, дневной прогноз минимум на 30 дней, дата/сумма/обоснованная
вероятность риска, график/предупреждения, проверка качества и реальная демонстрация.
Ручной/файловый источник будущих событий допустим по уточнению эксперта.
Ограничения исторического backtest не должны исключать весь известный календарь
из рабочего прогноза. Избежать двойного учёта регулярности и явных платежей.
`null` вероятности честно обозначает ограничение, но не закрывает требование ТЗ.

P1 после рабочего P0: первая полезная «что если», остальные сценарии, полная
история графика/план-факт, моки ФНС/1С, приглашения и восстановление. Эти функции
остаются в целевом плане. Вход/регистрация/выход и доступ к компании нужны P0;
доставка писем и завершение дополнительных Auth-функций не блокируют финансы.
Использовать существующие компоненты и сервисные границы; новые брокеры/сервисы
и замена уже работающих библиотек в ближайшую поставку не входят.
