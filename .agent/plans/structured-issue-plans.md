# Поэтапный формат автоматически создаваемых планов

Статус: все три этапа приняты разработчиком; локальная реализация завершена.
Итоговый апрув, включая исправления ревью, получен 2026-10-22.
Режим ревью: после каждого этапа — обязательная остановка до ревью и апрува
разработчика. Итоговое ревью вместо промежуточных здесь не выбрано.

## Цель и текущее состояние

Сделать формат автоматических `/create-plan` и изменений плана через `/discuss`
соответствующим ADR-020 и правилам `.agent/workflows/issue-planning.md`.

На старте задачи `steps` в `.agent/infra/planning/plan_policy.py` — список строк, а
`render()` выводит его как плоский список «Шаги исправления». Исходная инструкция в
`.agent/infra/planning/ssh_plan.py` запрашивает предлагаемые шаги, но структура
отдельного этапа не проверяется. Одна смена инструкций не гарантирует
структурированный формат ответа runner и итогового Markdown.

## Решения и границы

Принято: каждый этап имеет результат, границы, зависимости, действия, проверки,
критерии завершения и статус. Новый план не утверждает, что реализация или
проверки уже выполнены. На каждом этапе реализации действует ревью разработчиком;
исключение возможно только по явно согласованному намерению разработчика
из ADR-020. Определять намерение по смыслу плана или прямого поручения,
без дословного сравнения с фразой. Агент не выбирает режим самостоятельно.

В скоупе: схема/валидация планов, prompt, Markdown и соответствующие регрессии.
Сохранить границы исходной задачи, проверку SHA, ссылки на строки исходников,
фиксированный путь файла, защиту от дублей и существующие имена веток.
Не переоткрывать принятые этапы без поручения разработчика.

Вне скоупа: автоматическая реализация этапов, новые команды запуска кода,
автоматические commit/push/merge/deployment, изменения Fadwix или GBrain.

## Этап 1 — структура этапов и её валидация

Статус: Принят.
Зависимости: отсутствуют.
Результат: этапы представлены проверяемыми объектами вместо произвольных строк.

Затрагиваемые файлы:
- `.agent/infra/planning/plan_policy.py`
- `.agent/infra/tests/test_staged_planning.py` (новые регрессии;
  использует существующие фикстуры из `test_planning.py`)

Работы:
- [x] Определить структурированный `stages` с полями из ADR-020 и заменить
  плоские `steps` в формате создаваемого/изменяемого плана.
- [x] Валидировать обязательные поля, порядок/зависимости, допустимые статусы
  и выбранный разработчиком режим ревью.
- [x] Сохранять историю принятых этапов при изменении существующего плана;
  не принимать выдуманное моделью подтверждение пользовательского ревью.
- [x] Учесть существующие планы со строковыми шагами: их обновление должно
  сохранять согласованные требования, путь файла и ветку.

Проверки и критерии завершения:
- Новый план содержит минимум один осмысленный этап со статусом «Не начат».
- Пустые/неполные этапы и самовольный выбор исключения ревью отклоняются.
- Проверки идентичности Issue, SHA и допустимого назначения сохраняются.

Результат этапа 1:

- Добавлены `STAGE_SCHEMA`, `STAGED_SCHEMA` и `validate_staged_report()`. Поля
  этапа: `number`, `title`, `result`, `status`, `depends_on`,
  `external_dependencies`, `affected_files`, `actions`, `checks`, `acceptance`.
  Нумерация последовательна, зависимости ссылаются только на предыдущие этапы,
  файлы входят в общий список затрагиваемых путей.
- Режим `per-stage` действует по умолчанию; `after-all` требует явного
  `approved_review_mode` от доверенной вызывающей стороны. Статусы сохраняются
  из доверенного `previous_plan`, принятые этапы неизменяемы. Модель не может
  самостоятельно повысить статус; текст комментария/Markdown не является
  доказательством апрува.
- Старый отчёт со `steps` поддержан как исходные данные перехода: новый план
  получает не начатые этапы, сохраняя привязку Issue/SHA/ветки и фиксированного
  пути. Это не превращает текстовые утверждения старого плана в апрув этапов.
- Пройдены 13 новых профильных тестов и все 70 инфраструктурных тестов, Ruff
  lint/format, actionlint и `git diff --check`.
- Перед отдельным коммитом этапа 1 проверен изолированный снимок индекса:
  все 48 тестов этого снимка и проверки Ruff пройдены. Последующие изменения
  команд обсуждения в этот коммит не включены.

Граница этапа: активные SSH/publisher/renderer продолжают использовать прежнюю
схему `SCHEMA`. Новый формат добавлен отдельно, чтобы этап 1 оставался рабочим
без преждевременного переключения читателей/писателей. Их согласованное
подключение, читаемый Markdown и выбор источника доверенных подтверждений
относятся к этапу 2. Проверка реального runner и публикация не выполнялись.

Ревью этапа 1 пройдено; 2026-10-22 разработчик разрешил переход к этапу 2
и отдельно поручил закоммитить этап 1. Публикация и развёртывание не запрошены.

## Этап 2 — инструкция модели и читаемый Markdown по этапам

Статус: Принят.
Зависимости: принят этап 1.
Результат: сгенерированный план показывает отдельные этапы и точки ревью.

Затрагиваемые файлы:

- `.agent/infra/planning/plan_policy.py`
- `.agent/infra/planning/github_plan.py` — согласованное подключение обработчиков
  подготовки, проверки и публикации нового формата.
- `.agent/infra/tests/test_planning.py`
- `.agent/infra/tests/test_staged_planning.py`

- [x] Сохранять краткую оценку границ Issue без заявления о выполнении плана.

Проверки и критерии завершения:
- Пример из `.agent/prompts/local-plan.md` воспроизводится по структуре.
- По умолчанию план требует остановку после каждого этапа; согласованное
  исключение переносит ревью в конец без автоматического принятия этапов.
- Предложенные действия/проверки не помечаются выполненными.

Результат этапа 2:

- Обработчик SSH и обе стороны публикации используют `report_schema()` и
  `validate_response()`: краткий отчёт границ задачи сохраняет `steps`, создание
  и изменение файла плана требуют `stages`. Старый ответ сервера для нового
  плана отклоняется, а не публикуется частично.
- Markdown содержит цель, исходники, границы, файлы, отдельные этапы с номерами,
  статусами, результатами, зависимостями, действиями, проверками, критериями
  завершения и точками ревью. Проверки и действия показаны как предлагаемые;
  новые этапы не выдаются за выполненные.
- Структурированное состояние сохраняется в служебном комментарии внутри
  единственного файла плана. При следующем изменении оно считывается из Git
  по проверенному пути и SHA. Перед записью обработчик публикации повторно
  получает этот файл; подмена состояния в переданном результате отклоняется.
  Расхождение Markdown и служебного состояния также прерывает обновление.
- Режим ревью нового плана — поэтапный. Режим и статусы предыдущего
  структурированного плана сохраняются; принятые этапы защищены от изменений.
  Старый Markdown без структурированного состояния переводится в новый формат
  со статусами «Не начат», его текстовые утверждения не считаются апрувом.
  Автоматическое распознавание новых подтверждений статусов и смены режима
  из комментариев не добавлялось: модель не получает такую власть.
- Лимит файла плана увеличен до 128 КиБ для текста и служебного состояния;
  ограничение структурированного ответа в 45 000 символов сохранено.
- Пройдены все 80 инфраструктурных тестов и проверки Ruff. Проверки используют
  заглушки GitHub и модели; реальных обращений к модели и серверу не было.
  Проверки публикации сохраняют фиксированный путь, `feat:`, прямую ссылку
  на запрос и обновление ветки без принудительной перезаписи.

Ревью этапа 2 пройдено; 2026-10-22 разработчик дал апрув после обсуждения
сохранённого состояния и условий отправки инструкции модели.

## Риски и вопросы

Нужно отдельно согласовать публикацию и установку, затем провести реальные
проверки протокола. Старые планы без служебного состояния переводятся в новый
формат с не начатыми этапами; текстовые утверждения о ревью не становятся
подтверждёнными статусами. Автоматическое принятие новых подтверждений и смены
режима из комментариев не добавлено. Ручные изменения плана должны сохранять
соответствие видимого текста и структуры, иначе обновление останавливается.
Нужны согласованные версии серверных и GitHub-обработчиков; локальные тесты
не подтверждают работу обновления на сервере. Общий диалог Issue/PR и закрытие
Issue при передаче в PR остаются отдельной реализацией ADR-021.
