# Документация к приложению Saldo Analytics

## Приветствие

Привет. Если тебя заинтересовал исходный код Saldo Analytics, здесь можно разобраться, как устроен фронтенд, запустить его у себя и подготовить демонстрацию для хакатона.

## О проекте

Saldo Analytics — сервис финансового прогнозирования для малого бизнеса. Он помогает увидеть будущий остаток денег, заметить ожидаемый кассовый разрыв и оценить последствия изменений в платежах.

В этой версии есть регистрация, вход и восстановление доступа, подтверждение кодом, финансовый дашборд, личный кабинет с выходом и юридические страницы. Дашборд показывает баланс, предупреждения и график прогноза на 30, 60 или 90 дней.

Для компаний, участников, операций, платежей, импортов, интеграций, прогнозов и сценариев подготовлены типизированные API-сервисы. Наличие сервиса не означает, что для каждой операции уже создан отдельный экран. В режиме mock демонстрация работает без backend; реальная интеграция зависит от реализации API.

## Быстрый запуск

Для разработки и проверок используй Node.js 24 и npm. Все команды ниже выполняются из каталога `frontend/`.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

Приложение откроется по адресу [localhost:3000](http://localhost:3000). В примере окружения включён mock, поэтому отдельный сервер для знакомства с интерфейсом не нужен.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `developerMode` | Только точное значение `mock` включает моки. `dev`, `test`, `MOCK`, любое другое значение и отсутствие переменной используют реальное API. |
| `NEXT_PUBLIC_API_URL` | Базовый адрес API. По умолчанию `/api/v1`; для отдельного backend укажи его доступный браузеру адрес. |

Настройки попадают в браузер при сборке. После изменения окружения перезапусти dev-сервер, а для production пересобери приложение. Переменные `NEXT_PUBLIC_` открыты посетителям: секретам в них не место.

## Режим mock

```dotenv
developerMode=mock
```

Моки основаны на телах ответов из backend-контракта. Все 54 операции работают через локальный Axios-адаптер: регистрация и сессии, компании, участники и приглашения, баланс, операции, платежи и сопоставления, импорты, подключения, прогнозы и сценарии.

Данные и демо-сессия сохраняются в `localStorage` под ключом `saldo-mock-state-v1` и переживают перезагрузку. Пароли не сохраняются. Для возврата к исходной демонстрации удали этот ключ в своём браузере и перезагрузи страницу.

Форма входа проверяет формат почты и требует пароль, содержащий хотя бы один непробельный символ. В mock подходит любой такой пароль. Для подтверждения регистрации, входа и сброса подойдёт любой шестизначный код. Нули в ячейках — плейсхолдеры. Письма не отправляются, запросов CSRF и обращений к реальному API в mock нет.

Подтверждение регистрации сразу создаёт демо-сессию и открывает дашборд. При входе сессия активируется только после подтверждения кода. После подтверждения сброса открывается форма нового пароля, затем страница входа.

Ответы задерживаются на 300 мс. Изменения доступны последующим запросам; списки поддерживают фильтры и пагинацию. Версии проверяются, а повтор действия с тем же `Idempotency-Key` не создаёт повторную запись. Отмена запроса не меняет данные.

Импорт имитирует обработку файла на демонстрационных записях и не разбирает настоящий CSV. Прогноз рассчитывается по демо-платежам; внешние интеграции и ML не вызываются. Два дополнительных маршрута подтверждения входа и сброса существуют только внутри mock-адаптера и никогда не отправляются в реальное API.

## Авторизация

При регистрации проверяются имя, фамилия, почта, пароль, повтор пароля и две независимые отметки: согласие на обработку данных и ознакомление с политикой конфиденциальности. Frontend получает полный активный текст через `GET /auth/personal-data-consent` и показывает его рядом с отдельной, изначально пустой отметкой. Подтверждение передаётся с версией именно этого документа и SHA-256. После `CONSENT_DOCUMENT_CHANGED` текст загружается заново, отметка снимается и требуется новое явное согласие; автоматического повтора регистрации нет.

Валидация форм выполняется в TypeScript, нативная HTML-валидация отключена. При входе проверяются формат и заполненность почты и непустой пароль; правила нового пароля к существующему не применяются. Ошибки регистрации, восстановления и подтверждения показываются снэкбаром.

Защищённые страницы проверяют `/me`. Если вход подтвердить не удалось, пользователь попадает на `/login`. Подтверждённый пользователь на страницах авторизации перенаправляется на `/`; пользователь с неподтверждённой почтой может открыть `/verify-code` и запросить новый код. Политика и согласие доступны всем и всегда; циклических редиректов между ними и авторизацией нет.

Реальный API использует cookie-сессии и CSRF перед изменениями. Access/refresh-токенов и endpoint обновления сессии в текущем контракте нет. При `401` клиент требует нового входа и не повторяет изменения автоматически. Флажок «Запомнить меня» сохраняет только почту.

Подтверждение почты передаёт `{challenge_id, code}`: handle из register/resend и строку из шести ASCII цифр, включая ведущие нули. Handle заменяется после resend, срок — 10 минут; при потере handle можно указать почту и запросить новый код. Подтверждение не создаёт сессию: после успеха открывается вход. Дополнительные подтверждения входа и сброса кодом остаются только mock-UX, настоящий reset использует отдельный token из ссылки. Go API и бизнес-RPC Auth ещё не реализованы; эти изменения согласуют клиент с контрактом, не доказывают backend E2E.

## Дашборд и график

Дашборд получает компанию, актуальный баланс и прогноз через сервисы. Дата баланса используется как дата отсечения прогноза. Готовый подходящий прогноз используется повторно; для нового запуска клиент ожидает результат фонового задания.

График построен на Recharts. По горизонтали расположены дни, по вертикали — суммы в рублях. Линия появляется с ускорением. Подсказка сохраняет точность исходной денежной суммы, даже если она больше безопасного целого JavaScript. Предупреждение определяется по `first_gap` из API и описывает ожидаемый разрыв, а не факт неплатежа.

Периоды переключаются между 30, 60 и 90 днями. Пока данные загружаются, все три переключателя заменяются одним спиннером без изменения высоты блока. На мобильном сначала идёт график, затем карточки; на ПК расстояние между карточками слева — 30 px.

## API-сервисы

Контракт расположен в [`docs/api/openapi.yaml`](../docs/api/openapi.yaml). Это проект API; наличие типов и моков не подтверждает готовность реального backend.

- `src/interfaces/<категория>/request.ts` и `response.ts` — параметры и ответы. Общие сущности находятся в `Entities.ts`.
- `src/service/<категория>_service` — типизированные методы с необязательным `AbortSignal`.
- `src/service/api.ts` — Axios, cookie, CSRF и единая обработка ошибок.
- `src/mock/bodies.json` — примеры тел backend; `responses.json` — 54 маршрута и статусы, `authResponses.json` — два подтверждения только для mock.

Деньги в минимальных единицах и версии остаются строками, даты сохраняют формат API, `null` не подменяется. Идентификаторы кодируются для URL. Для изменения с идемпотентностью вызывающий код передаёт ключ: один ключ для повторов одного действия, новый — для нового действия.

Загрузка CSV передаёт `File` через `FormData`; boundary устанавливает браузер. Ошибка HTTP возвращает отклонённый Promise и показывает текст `error.message`. Если текста нет, используется «Не удалось выполнить запрос. Попробуйте ещё раз.». Отмена запроса не создаёт уведомление.

## Интерфейс и стили

Цвета, шрифты и длительность переходов находятся в `src/app/global.scss`. Стили компонентов — в `style.module.scss`, импортируются как `styles`. Фон всех страниц — `#EAEAEA`, стандартный transition — `0.3s`; учитывается `prefers-reduced-motion`.

Хедер скрыт на страницах авторизации. Логотип банка ведёт на главную, название компании и аватар объединены в ссылку на кабинет. Если картинки аватара нет, показывается первая буква по центру. На мобильном до 480 px используется компактный хедер.

Формы имеют максимальную ширину 750 px и отступ от краёв минимум 10 px. Видимые лейблы над полями есть только во входе и регистрации. Поля в фокусе светлеют, недоступные элементы имеют прозрачность 40%. Иконки пароля всегда имеют прозрачность 40%, без hover-анимации.

При отправке запроса спиннер заменяет содержимое кнопки, сохраняя её размеры; повторные нажатия блокируются. Checkbox анимируется при установке и снятии отметки, расстояние до текста — 10 px, hover-анимации нет.

Полоса прокрутки оформлена глобально: фон дорожки совпадает с фоном страницы, ползунок чёрный и скруглённый. Для браузеров WebKit/Chromium толщина — 8 px; Firefox использует тонкую полосу с теми же цветами.

## Снэкбары и пасхалка

Для предупреждения, информации, ошибки и успеха есть отдельные компоненты MUI и функции `showWarningSnackbar`, `showInfoSnackbar`, `showErrorSnackbar`, `showSuccessSnackbar`.

Уведомления появляются сверху по центру, выезжают из-за верхнего края и уходят обратно за 300 мс. Очередь показывает их по одному без одинаковых дублей. Закрытие доступно кнопкой, Escape и автоматически через 6 секунд; следующий снэкбар появляется после завершения анимации предыдущего.

Через 3 минуты после открытия приложения появляется информационный снэкбар с комплиментом. Следующие показываются через случайный промежуток от 5 до 120 минут. Переходы между страницами не сбрасывают таймер.

SVG-иконки уведомлений и паролей взяты из [Tabler Icons](https://github.com/tabler/tabler-icons), лицензия MIT. Файлы лицензий находятся рядом с иконками в `public/icons`.

## Юридические документы

Страницы политики и согласия — серверные компоненты. Они выводят текст из `src/content/*.json` сразу в HTML: заголовки, параграфы, списки и таблицы. Отдельного API-запроса за текстом нет. Стили тегов ограничены страницами документов.

Документы используют название Saldo Analytics и реквизиты ПАО КБ «Центр-инвест» из [официальных сведений банка](https://www.centrinvest.ru/files/about/requisites.pdf). Это проекты документов. Перед реальным подключением редакцию `saldo-2026-10-24` и SHA-256 согласия необходимо согласовать с backend; нельзя незаметно подменять версию или отправлять другое содержимое с прежним хешем.

## Демонстрация и CI deploy

Mock-фронтенд размещается на [saldo.brokebyte.me](https://saldo.brokebyte.me)
в отдельном Docker Compose проекте: Nginx завершает TLS и передаёт запросы
в Next.js standalone. В образ при сборке явно передаётся `developerMode=mock`;
данные и сессия остаются локальными в браузере. Backend и ML не вызываются.

Workflow `frontend.yml` проверяет линтер/типы, тесты и Docker-сборку в PR.
После push в `main` он публикует образ в GHCR. Только явный ручной
`workflow_dispatch` на `main` развёртывает его по immutable digest. PR не получает
ключ деплоя и не запускает deployment. Конфигурация сервера и TLS устанавливается
администратором отдельно; workflow обновляет только контейнер Saldo frontend.

[Инструкция по установке, секретам CI, TLS и откату](../deploy/frontend/README.md).

## Docker

```bash
cp .env.example .env.local
docker compose --env-file .env.local up --build -d
```

Сайт доступен на порту **3000**. Dockerfile использует многоэтапную сборку Node.js 24 Alpine и Next.js standalone. В runtime работает пользователь `node`; копируются только сервер, зависимости, static и public.

`developerMode` и `NEXT_PUBLIC_API_URL` передаются как build args. При их изменении пересобери образ. `.dockerignore` исключает зависимости, сборки, Git и локальное окружение.

## Проверки

```bash
npm test
npm run typecheck
npm run lint
npm run build
```

Тесты проверяют mock-маршруты, изменение и сохранение данных, авторизацию, отмену запросов, отсутствие реальной сети и автоматического CSRF в mock. Отдельно проверяются реальные режимы транспорта, валидация форм, точность сумм, таймер комплиментов и редиректы авторизации.

После сборки проверь вход с кодом, регистрацию, восстановление, перезагрузку дашборда, все три периода графика, выход и прямые ссылки на документы. Для мобильной версии проверь ширины 320–480 px, порядок блоков и отсутствие горизонтального переполнения страницы.
